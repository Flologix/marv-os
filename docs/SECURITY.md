# Security model

**Principle:** prompt injection can't be filtered out, so it's contained. An injected model must never hold all three of these together:
- private data;
- untrusted content in its context;
- a way out (network, the mesh, or code that runs outside the sandbox).

These rules are requirements for the Rust build from day one. They come from a security review of Marv 0.3.0 (2026-10-12); see the repository's security advisories.

## Process and launch
- **One static binary.** No interpreter reads the project's `bunfig.toml`, `.env`, `node_modules` or similar. Config comes only from:
  - `~/.marv/` (or `$MARV_CONFIG_DIR`, but only from the real environment, never from a file in the project);
  - the project's `.marv/` (trust-gated) and `.mcp.json` (trust-gated).
- **A project's `.marv/config.json` may set only an allow-list of keys, and it fails closed.** The order is the person's `~/.marv/config.json`, then the project's file, then env and flags. The project's file may set `formatter` and `checks` (settings for its own code: the formatter still runs inside the sandbox, and the person's own `false` for either still wins) and `"yolo": false` (it only narrows; `"yolo": true` is ignored). Every other key, today's (`model`, `provider`, `apiKey`, `baseUrl`, `sandbox`, `approve`, `writable`, `hooks`, `mesh`, `herdr`…) and any added to the person's config later, applies nothing and is named in one startup note (`marv_session::project_config::PROJECT_KEYS`; a new project key is a decision, made by adding it there). The file is read like skills: a regular file inside the project after realpath, opened non-blocking, at most 1 MB; where it is the person's own config (Marv started in the home folder) it's not a project's. `/yolo on` in a project that narrows yolo off says so and changes nothing; Marv desktop reads the chat folder's file the same way (`marv_web::host::project_config`), its note a notice in the chat, and holds yolo off whatever the chat's settings say. **Until the person trusts the project, its config only narrows:** a formatter map and `"checks": true` (they run commands from the project's files) are ignored and named in the note; `false` values and `"yolo": false` apply (guard `boot.rs::an_untrusted_projects_config_only_narrows`). Its `.marv/checks` files are held back the same way: checks are off for the whole session (so a check file that arrives later doesn't run either), the note names each, cut, cleaned and counted like every name a project's config puts in a note (and `marv -p` prints it through `printable()`), and `/checks on` says why (guard `boot.rs::an_untrusted_projects_checks_dont_run`). Each shell asks #220's project trust (`project_trust::config_trusted`): only a project whose files the person trusted with `/trust` (`TrustStatus::Trusted`, exactly those contents) or a `marv -p --trust-project` run widens; a repository with nothing else to trust (`Nothing`) still only narrows (guard `boot.rs::a_projects_config_widens_only_once_the_person_trusted_its_files`). The config file itself isn't among the hashed files (a trusted project's later change to it applies unasked: a known limit). Guards: `tests/guards/tests/boot.rs` (`a_project_config_sets_only_its_allow_list`, `a_projects_narrowing_reaches_marv_p_and_its_widening_doesnt`).
- **Session-start hooks come only from the user's own config (#108).** `hooks.sessionStart` is read from `~/.marv/config.json` (or `$MARV_CONFIG_DIR`'s) and nowhere else: `hooks` isn't on a project config's allow-list (above), and a project's `.marv/config.json` naming `hooks` is refused with a startup note and never run (it's only looked at if it's a regular file inside the project, and read up to 1 MB) (cloning a repository must not run its commands, the class of hole 0.3.0's `bunfig.toml` preload was). Hooks run outside the sandbox without asking, since the user wrote them: with the host door's environment (Marv's keys and secret-looking variables left out), a timeout (default 15 s, the process group killed) and an 8 KB output cap. The user's config is out of the sandbox's reach (a stand-in home; when the project is the home folder, the home is read-only in the sandbox with `~/.marv` hidden, and `.marv/**` is protected for the edit tools), so the model can't plant a hook either. **Their output taints the session** when it's sent (`Provenance::Hook`) and is fenced as data (`<untrusted-data source="hook">`): the user chose the command, not what it prints (`bd ready` lists issue titles anyone can file on a public repository). Only `"trusted": true` on a hook in the user's config opts it out; empty output taints nothing. Guards: `tests/guards/tests/launch.rs` (`a_projects_session_start_hooks_never_run`, `marv_p_never_runs_a_projects_hooks`, `hook_output_taints_the_session`).
- **Saved sessions and trajectories hold prompts and code.** They're written under Marv's config folder only (`sessions/`, `trajectories/`; 0600 files in 0700 folders), never into the project. A desktop chat follows the config's `trajectories` as the TUI and `marv -p` do (#204). The shared `marv-web` server does the same with its own config (`<data>/marv/config.json`, on by default), so it keeps every visitor's prompts and code: an operator who doesn't want that sets `"trajectories": false` there (app/README.md).
- **Model output is never written to the terminal raw.** Every string goes through `printable()`, which strips CSI/OSC/DCS, C0/C1 controls and bidi overrides. This includes headless text mode.

## Sandbox (`marv-sandbox`)
- **bubblewrap**, with:
  - read-only system directories and an empty `/run` (except the mesh plug, `/run/marv/mesh.sock`, and the process door's relay: Marv's binary at `/run/marv-bin` and socket folders under `/run/marv`);
  - a stand-in home, with toolchains re-mounted read-only and credential files masked;
  - the project writable, with `.git` and **protected paths** read-only;
  - Marv's config folder (`~/.marv`, or `MARV_CONFIG_DIR` wherever it is) hidden;
  - no network unless approved (`--unshare-net`), a cleared environment, and its own PID namespace.
  - what a command leaves running ends with it, a background job that still holds the command's output pipes included (`cd dir && server > log 2>&1 &`). Outside the sandbox the bash call ends at the shell's exit and leaves such a job running (marv-rs, Terminal-Bench 2026-11-06); in the sandbox that never applies. Guard: `tests/guards/tests/sandbox.rs::a_sandboxed_background_job_that_holds_the_pipes_ends_with_the_command`.
- **On macOS (Seatbelt, #166), `marv __guard` stands in for the PID namespace.** It runs each sandboxed command in a session and process group of its own, kills that whole group (itself included) as soon as Marv exits, panics or is killed (it polls its parent every 200 ms), and passes a stop on to the group; Marv's timeout and stop `killpg` the group, and so does the command's normal exit: once the guard has exited (seen before it's reaped, so its group's id can't be reused), whatever the command left running in the group (`sleep 600 &`) is killed before its output is read to the end; a command whose turn is dropped takes its group with it. **Known limit:** a process that leaves the group itself (`setsid`, `setpgid`) and double-forks can outlive the command and Marv. It stays inside the sandbox (Seatbelt is inherited and can't be dropped), so it can do no more than the command could, but nothing sweeps it up; bwrap's PID namespace closes this on Linux. The guard shares the command's sandbox and group, so the command can also SIGKILL or SIGSTOP the guard; its group then outlives a Marv that crashes or is SIGKILLed (a Marv that exits normally, or times the command out, still kills the group). A guard that can't have a session of its own runs nothing. Tests: `crates/marv-cli/tests/guard.rs` (`nothing_in_the_group_outlives_a_parent_killed_with_sigkill`, `a_stop_reaches_everything_in_the_group_and_the_guard_exits_with_the_commands_code`); in the sandbox, `tests/guards/tests/seatbelt.rs` (`nothing_outlives_the_command_and_an_escapee_stays_sandboxed`, `a_dropped_command_takes_its_group_with_it`).
- **A sandboxed command without network runs without asking (`approveSandboxed`, default `auto`), yolo or not; in a woken turn with the project read-only.** `bash` with the working sandbox, no `network`, no `git_write` (unless the next rule lets it) and no `sandbox: false` runs confined (`.git` read-only) in a turn the person started, and in a turn a mesh wake started (`CallMode::runs_sandboxed_unasked`; `Tool::auto_sandboxed`). A wake's turn is not a person's (#74: another agent's message never auto-approves anything), so there the project is mounted **read-only** (`CallMode::sandboxed_unasked_project_read_only`, `ToolContext::project_read_only`): it may inspect, build into the sandbox's `/tmp` and run read-only checks unasked, and a command that has to change the project (a Makefile, a workflow, `build.rs`, `sed -i`) fails on the read-only mount with a note, or asks (`git_write: true`; `edit_file` and `write_file` ask as before). The person's turn keeps it writable. It never applies in `marv -p` (`--approve` stays the contract), a radio turn, a woken turn's subagent, or with the sandbox off or unavailable. It does apply where the project is the home folder or above it (yolo is refused there): the sandbox shows the project read-only there, so such a command can write only to `/tmp` (guard: `marv-session`'s `approve_sandboxed_holds_in_the_home_folder_but_never_in_marv_p`). It is checked after the taint rules: network and egress ask when tainted, protected paths ask. The default is `auto` unless the config sets `yolo` to `false` (nobody who turned yolo off is upgraded silently) or `MARV_YOLO=off` is set (a worker the Herdr door spawned never exceeds its parent); an explicit `approveSandboxed` in the file always wins, except against `MARV_YOLO=off`. `"approveSandboxed": "ask"` in the user's config restores asking, and `/yolo off` does the same when the file doesn't say `approveSandboxed` itself. Guards: `tests/guards/tests/approvals.rs` (`sandboxed_commands_without_network_run_unasked_in_person_and_woken_turns`, `a_woken_turns_unasked_sandboxed_commands_can_read_the_project_but_not_change_it`, `approve_sandboxed_ask_headless_and_radio_turns_still_ask`, `approve_sandboxed_still_asks_for_network_git_write_the_host_and_without_a_sandbox`, `approve_sandboxed_leaves_taint_rules_alone`).
- **Protected paths ask even in yolo, and are read-only inside the sandbox:**
  - `.git/` and the `core.hooksPath` folder;
  - `.env*`, `.envrc`, `bunfig.toml`, `.mcp.json`;
  - `AGENTS.md`/`CLAUDE.md` at any level, and `.marv/**`;
  - `.vscode/`, `.idea/`;
  - `package.json` lifecycle `scripts`;
  - names match in any letter case on every OS, and on Windows as NTFS reads them (trailing dots and spaces, 8.3 short names such as `GIT~1`, and `name:stream` as `ProtectedRule::StreamName`); the home folder comes from `USERPROFILE` when `HOME` is unset (guards `protected_names_ask_in_any_case_and_in_ntfs_spellings` and `the_home_falls_back_to_the_windows_profile`, `tests/guards/tests/sandbox.rs`);
  - when the project is the home folder (or holds it), where `edit_file`/`write_file` run outside the sandbox and reach the whole home: every hidden top-level entry of the home (`~/.bashrc`, `~/.profile`, `~/.config/systemd/user/`, `~/.config/autostart/`, `~/.ssh/authorized_keys`, `~/.local/bin/`…) and the hooks folder (`core.hooksPath`) of the global git config and of any repository in the home (`home_rule`; guard `in_the_home_folder_dotfiles_and_hooks_ask_even_in_yolo`).
  - `apply_patch` (#66, not offered yet) is judged exactly like `edit_file`/`write_file` on **every** path it names: a Move's source (moving a protected file away deletes it) and its destination (moving a harmless file onto `.envrc`, `AGENTS.md` or a hooks folder writes there) both count, the home folder's rule included; the `package.json` rule runs on every `package.json` a patch leaves (updated, added, or a Move's destination, judged against what is at that path now, never the source's content). One protected path makes the whole patch ask. Every path is resolved inside the project twice (the plan, and the lock taken before the write). Guards: `tests/guards/tests/apply_patch.rs`.
- **Only the person's own files choose another provider.** An agent type's `model:` may name a model on another provider (`zai/…`, `chatgpt/…`, `ollama/…`, `openrouter/…`) only in `~/.marv/agents`; one in a project's `.marv/agents` is refused before any core is made or anything is sent (the model reads why), so a repository can't pick where your code goes. `smallModel` comes only from the user's own config. A project's `model: small` gets the small model only when it is on the chat's provider. A cross-provider subagent inherits taint and approvals as any subagent does, and a worktree subagent's approval names its core. Guard: `tests/guards/tests/cores.rs` (`a_projects_agent_type_cant_name_another_provider`).
- **Secrets** (`.env*`, `*.pem`, `id_*`) need approval to read, and are masked in the sandbox.
- **A chat's `/tmp` is its own scratch folder (bubblewrap, Linux only).** On macOS (Seatbelt) each command still has its own private `$TMPDIR`, removed after it, and the prompt says so. Instead of an empty tmpfs per command, `/tmp` is the chat's `<id>.swap/tmp` (0700, never through a symlink), bound read-write before anything is hidden, so files persist between that chat's commands (background processes keep their own empty tmpfs). Over `swap::SCRATCH_CAP_BYTES` (512 MB) when the session starts or resumes it is emptied, and bun's download cache stays a per-command tmpfs inside it (`/tmp/bun-cache`), so nothing one command downloads is there for the next. It is per conversation id (another chat, `/clear`, a resume of another chat: a different folder), lives inside the saved session's swap folder (deleted with the session; the usual swap cleanup ages it out), holds nothing Marv reads back, and gives a command no more reach than the empty tmpfs did, since the folder is only ever its own chat's. Subagents share their chat's. Guards: `tests/guards/tests/sandbox.rs::a_chats_tmp_survives_between_commands_and_isnt_shared`, `bwrap.rs`'s `tmp_is_the_sessions_scratch_folder_when_it_has_one_else_an_empty_tmpfs`.
- **In the home folder, the sandbox shows the home read-only and hides Marv's config, credentials and agent sockets.** When the project is the home folder or a parent of it (`/`, `/home`), a stand-in home would hide the project, so instead the project is mounted read-only (never read-write), and on top of it every hidden top-level entry of the home (`~/.<anything>`: `~/.marv`, `~/.ssh`, `~/.gnupg`, cloud CLI folders, `~/.claude`, `~/.config`, `~/.local`, `~/.cache`) is hidden, apart from the toolchain folders (shown read-only, credential files masked) and, on Linux, the desktop's and apps' settings (`HOME_SHOWN`: `~/.config`, `~/.local/share`, `~/.local/state`, shown read-only; the settings are what a person asks about in `~`, and reading them otherwise took a command outside the sandbox, asked each time), in which browser profiles, password managers, chat apps and CLI and agent logins (`HOME_MASKS`), apps' web storage folders (`secret_dir_name`: `Local Storage`, `IndexedDB`…) and files named like secrets (`secret_name`: `auth.json`, `*token*`, `*credential*`, `*.pem`, `*.key`…) found by the bounded scan stay hidden; the named ones (`~/.config/herdr`, `~/.config/gh`, `~/.docker`, `~/.kube`, `~/.local/share/keyrings`…) stay hidden even if a toolchain mount would show them, and every Unix socket or FIFO a bounded scan finds in the visible part of the home is replaced by `/dev/null` (a read-only mount doesn't stop a `connect()`). Sandboxed commands write only to `/tmp` there; the edit tools keep their approvals, a change to a dotfile or a git hooks folder there is a protected path (it asks every time), and yolo is refused. Every other file change there (`edit_file`, `write_file`: a `Write` tool with the `files` scope) is asked `once` (`registry::home_file_write_once`), and never run on yolo even by a context that has it (`registry::home_file_write`): Yes or No, no "always"; neither a remembered "files" scope nor the config's `"approve": ["files"]` covers it (both go through `SessionApprover`, which never answers a `once` request), the TUI's "always" on another queued request doesn't answer it, and a worktree subagent's automatic yes (`SubagentApprover`) doesn't either. `marv -p --approve files` still approves it: the flag names the scope for that one run and answers "yes" per call (`ScopeApprover`), never "always". Guards: `tests/guards/tests/approvals.rs` (`in_the_home_folder_always_on_a_file_change_still_asks_the_next_time`, `in_the_home_folder_a_file_change_request_is_once`, `in_the_home_folder_config_approve_files_doesnt_cover_a_file_change`, `headless_config_approve_files_in_the_home_folder_is_refused`, `a_subagents_automatic_yes_doesnt_cover_a_once_request`, `a_project_under_the_home_keeps_always_for_file_changes`, `headless_approve_files_in_the_home_folder_still_writes`). One exception: a change whose every path lies, lexically and after realpath, in one visible two-level folder of the home (`~/Projects/shop`; `marv_sandbox::home::home_subfolder`; not a hidden entry at either level, not a folder on `PATH` or holding one) gets that folder's scope (`files:home:Projects/shop`, `registry::HOME_FOLDER_FILES`), which offers "always" for that folder alone; it's still never run on yolo, and a seeded "files" (the config's `approve`, the TUI's `--approve`) never covers it (`AlwaysScopes::contains`), only a person's answer for that exact folder; protected paths inside it keep asking every time (guard: `approvals.rs::in_the_home_folder_always_covers_one_visible_folder`). A home that can't be listed runs no command. An extra read-only or writable folder can never be the home or a parent of it. Guards: `tests/guards/tests/sandbox.rs` (`in_the_home_folder_no_socket_under_the_home_is_reachable`, `in_the_home_folder_credentials_and_marvs_config_are_hidden`, `in_the_home_folder_settings_show_and_their_secrets_dont`, `in_the_home_folder_nothing_in_the_home_is_writable`, `a_project_in_a_subfolder_of_the_home_stays_writable`). Marv desktop's Home chats run there under exactly these rules: a chat's folder may be the home folder itself (`check_chat_root`, never above it), while a space, a team, a rule and a grant still refuse it (`check_root`), and marv-web's host holds yolo off there whatever the chat's settings say (`yolo_refused`; test `a_home_chat_may_run_in_the_home_folder_and_nothing_else_may`).
- **The project's own tooling runs only inside the sandbox.** The typecheck, cargo check and pyright (#187) after an edit, the project's checks (`.marv/checks/`) and the project's formatter after an edit (#67) run in the sandbox, the project read-only, without network; without a sandbox they don't run at all, and Marv never installs a formatter. So their output never comes from a run with the network: it's the project's (quoted under Marv's note, not tainting), unlike an unsandboxed bash command's. The formatter is the project's own code, and it gets write to the one file being formatted — except on protected paths and `package.json`, which keep exactly what the edit tool wrote: a rewrite there could turn an approved diff into anything (a `postinstall` script into `package.json`, a planted `.vscode/` or `.marv/` file). A failing formatter's output reaches the model fenced as project data, like the checks'. A checker that keeps a build cache (#187) gets one writable folder, for that check only: exactly its repository's key folder in Marv's check cache (`~/.cache/marv/checks/<key>`, or `$XDG_CACHE_HOME/marv/checks`; `~/Library/Caches/marv/checks/<key>` on macOS), never the cache root, another project's key or the project's own build folder, and never added to the `writable` list. A key folder that is a symlink, not a folder or not the user's is refused; the cache is bounded (20 GB in all, least recently used first; 10 GB per key; nothing starts with less than 5 GB or 5% free; unused folders pruned after 14 days), and Marv sizes, prunes and deletes it without following links and without running anything on the host. Such a checker's warm-up starts only at a session's first edit, so a session that never edits never runs the project's build. cargo check runs the project's `build.rs` and proc macros, and project files steer it (`.cargo/config.toml`'s `rustc`, wrapper, linker, `[env]` and flags; `rust-toolchain.toml`): all of that runs only inside the sandbox, as it would for the model's own `cargo check` in `bash`, from the session's first edit on, with the project read-only, no network, `RUSTUP_AUTO_INSTALL=0` (Marv never installs a toolchain) and only its key folder writable; nothing project-steered runs on the host, and no cargo or rustup runs there even to detect it. pyright runs the project's own `.venv/bin/basedpyright` or `node_modules/.bin/pyright` when there is one (chosen by the command inside the sandbox, never looked up and run on the host), and it runs a Python interpreter the project's config can choose (`venvPath`/`venv`, whose `.pth` files run at startup): all of it only inside the sandbox, with the project read-only, no network and nothing writable. Whether a uv venv's interpreter is hidden is learned by reading the link on the host, never by running it. Memory isn't capped (there's no cgroup): a cold check of a big workspace can take a few GB. Guards: `checks.rs::a_check_writes_only_its_own_cache_key_folder`; `cargo_check.rs::a_malicious_build_script_runs_sandboxed_and_the_check_still_reports` (its `build.rs` can't write the project, another key or outside its key folder on the host, read a hidden home path or reach the network) and `cargo_check_tells_a_new_error_once_and_never_touches_the_projects_target`; `pyright_check.rs::a_projects_own_checker_runs_sandboxed` (a project's `.venv/bin/basedpyright` can't write the project or the real home, read a hidden home file or reach the host's loopback) and `pyright_tells_a_new_error_once_from_the_sandbox`; `marv-session`'s `diagnostics::machinery_tests::nothing_marv_does_around_a_check_runs_anything_on_the_host`.
- **Every path is checked after `realpath`.** No tool follows a symlink out of its root. That includes skill files, which the old code read outside the sandbox, and instruction files (`AGENTS.md`/`CLAUDE.md`: the project's, its parents', nested ones), which also never lead to a secret or into `node_modules`/`target`/`.git`; only the user's own `~/.marv/AGENTS.md` may link anywhere.
  - The one exception: a **personal** skill folder (`~/.marv/skills/<name>`) may be a symlink to a folder only root can change, such as Omarchy's `/usr/share/omarchy/…` (#75). That folder and every folder above it must be owned by root and not group- or world-writable. The skill is read from the link's real target, and its `SKILL.md` and files can't lead out of that folder. A project's skill folder never may.
- **The one read outside the project is the session's saved tool outputs (#61).** `read_file` and `grep` may read the files in `~/.marv/tool-output/<session>/`, and nothing else outside the project. Writing tools can't, and bash can't see the folder at all. A saved output keeps its source in its name (`<call id>.mcp.txt`), so an MCP server's text read back is fenced and taints as it did when it came; a long page web_fetch saves on its first read (#93) is `<call id>.web.txt` and reads back as web content.

- **On macOS (Seatbelt).** The macOS sandbox is built from the same plan as bubblewrap's (`marv_sandbox::seatbelt`, #164): a deny-default SBPL profile for `/usr/bin/sandbox-exec`, with reads allowed for the whole disk and then narrowed, writes only to the project, the writable extras and a private `TMPDIR`, and every path canonical and passed as a parameter, never written into the profile (a project path that can't be written into the protected-name regexes stops the command). It is the backend on macOS (#166): each command is `/usr/bin/sandbox-exec -p <profile> -D …= -- marv __guard <Marv's pid> -- bash -c …`, spawned with the plan's environment and nothing of Marv's (`sandbox-exec` passes its environment on). The guard binary is resolved once per run, and the availability checked once for it with the real base rules and the guard: with no `sandbox-exec`, a profile the kernel refuses, or a Marv already inside a Seatbelt sandbox, commands run unsandboxed with the warning, as on Linux without bwrap. What the profile assumes was checked on the macOS runner (`crates/marv-sandbox/tests/seatbelt_probe.rs`, results on #166). Seatbelt can refuse a path but can't show something else there, so these guarantees differ from bubblewrap's:

  | bubblewrap | Seatbelt | Mitigation | What's left |
  |---|---|---|---|
  | A stand-in home: empty, writable, thrown away | The home is unreadable and unwritable | Caches in the private `TMPDIR`; the home note says reads and writes there are refused | Tools that insist on writing `~/.something` fail instead of working on a throwaway copy |
  | Credential files read as empty | Reading them is refused | Denied by the path as written and where it leads | A tool that expects the file to exist and be empty errors out |
  | A private `/tmp` | `/tmp` is the host's | A private `TMPDIR` per command (0700, made by Marv, removed after, a new folder in the user's `/private/var/folders/<xx>/<id>/T/`, refused if it's inside or around the home, the project, `/private/tmp`, Marv's folders or an extra); `/private/tmp` and the user's `/var/folders/<xx>/<id>` denied (a command whose user folder can't be found doesn't start) | Tools that hard-code `/tmp` fail |
  | Its own PID namespace | None | Signals and process info only within the sandbox, process info denied explicitly first (Seatbelt's deny-default leaves every process of the same user readable: path, arguments, environment, descriptors); no `kern.proc.all` | Other processes' pids can be listed or guessed but not used |
  | Dies with Marv (`--die-with-parent`) | None | `marv __guard`: its own process group, watches its parent, kills the group when Marv dies; everything is killed on exit | A process that leaves the group and double-forks outlives the command, still sandboxed |
  | `--new-session` | No flag | `setsid()` in the guard, stdin `/dev/null`, terminals and pseudo-terminals denied | None known |
  | Its own loopback without network | None: loopback is the host's | Without network every IP connection is refused, loopback included. No port is opened one by one: Seatbelt's `localhost` matches every address of the machine, not just loopback | In-sandbox client/server tests need network (which asks) |
  | Protected paths mounted read-only | Write denies by path | The path and where it leads, `literal` and `subpath`; the protected names as case-insensitive regexes at any depth (outside `node_modules`, `target` and `.git`), so a command can't create them either; folders above a protected path can't be removed or renamed; the after-scan still runs | The after-scan is load-bearing for names: a protected name written inside `node_modules` or `target` (which the rules skip) and then moved out by renaming that folder isn't stopped by a rule, only found and reverted after the command; the same for a nested `.git` |
  | A hard link can't cross a mount (`EXDEV`) | Hard links are path operations | `link()` is checked against both the source and the new name, and is refused outright when the source can't be read or written (both probed): links are allowed only between files of the project and of the private `TMPDIR`, and nothing denied (the home, `~/Library`, the shared temporary folders, Marv's folders, credentials, protected paths and names, read-only folders) can be either end, so `ln ~/.ssh/known_hosts ./x` and `ln .envrc y` are refused | A hard link to a protected file made **outside** the sandbox beforehand can be written through from inside: the rules see its other name |
  | A home-folder project hides every hidden top-level entry | The same, by one regex, plus `~/Library` (where macOS keeps keychains, cookies, mail, messages and app data) | None needed | The rest of the home stays readable, as on Linux; Linux also shows `~/.config`, `~/.local/share` and `~/.local/state` again (`HOME_SHOWN`), which macOS keeps hidden |

## Doors out of the sandbox
Narrow, named ways out, each asked for and each with its own rule for what it can never do (Marv Sprint 4).
- **Process (#24, Marv #51):** a dev server or watcher that keeps running across turns.
  - It runs in its own sandbox, like a bash command's: it can't write outside the project, change `.git`, read the real home, or reach the host's network or `127.0.0.1` unless started with `network: true`.
  - Its ports are forwarded to the host's `127.0.0.1` only, never another interface.
  - A sandboxed command without network reaches its ports through the relay (`/run/marv/<id>`, the socket folder read-only), its own chat's and those of other chats in the same project folder in the same Marv (a team's devserver, `ProcessManager::forwards`), never another folder's. Those chats share the project's files already, and a process without network can't bring in outside text. Guard: `process.rs::a_sandboxed_command_reaches_a_process_another_chat_in_the_folder_started_and_no_other`.
  - Starting one asks, even in yolo; only the main agent can (a subagent's context has no door, refused before any ask). The one exception is `serve` with `approveSandboxed` on, in a person's turn (`ProcessTool::auto_sandboxed`): it runs Marv's own server, no project code, with the project read-only and no network, so it is no more than a sandboxed command without network; a woken turn still asks (guard: `process.rs::approve_sandboxed_serves_a_folder_unasked_but_a_start_still_asks`).
  - It dies on stop, when Marv exits or panics, and when Marv is killed (`--die-with-parent`).
  - `serve` (Marv's own static file server, `marv __serve`) runs with the project mounted **read-only**. It serves a build folder inside the project: never the project root nor a hidden folder (`.git`, `.marv`, any leading-dot component; `serve_folder`), and inside the folder never a hidden entry, by URL or through a symlink to one (the real path under the root is checked). It answers 403 unless the `Host` header is `localhost`, `127.0.0.1` or `[::1]` (DNS rebinding: a page the user has open can't read it through a name that resolves to 127.0.0.1). It takes at most 64 connections at once, times out a write after 10 s, backs off after accept errors, streams files and refuses one over 256 MB. Guards: `serve.rs` and `process.rs` unit tests.

## Provenance and taint (`marv-core::Provenance`)
- **Authority comes from the person and from Marv's fixed words. Everything else is data.** Every piece of text in a model's context has a source, in one of three classes (`marv_core::SourceClass`): *authority* (what the person types and answers, Marv's fixed text, the person's own files: `~/.marv/AGENTS.md`, personal skills, memory, their config), *workspace* (the project folder the person chose: its files, local git history, checks, the formatter, a subagent's report, and a trusted project's instruction files), and *outside* (web pages, MCP results, the mesh and the radio, Herdr reads, untrusted hook output, images, the GitHub door's output, the output of any command run with the network, a tainted subagent's report). Outside text is fenced as data and taints the conversation; workspace text is quoted where Marv speaks about it and never taints (tainting every read of every repository would make every session tainted). Data gains authority only through the person: an approval they answered, or a project whose instructions they trusted. Guards: `tests/guards/tests/untrusted_text.rs`.
- **Every tool declares its kind and its source.** `Tool::kind` and `Tool::provenance` have no defaults, so a new tool can't run unasked, or hand outside text over as the project's, by leaving them out; `run_tool` raises every result to the source its tool declares for that call (`Tool::provenance_in`: bash with the network, on the host, or anywhere the sandbox is off or unavailable (nothing takes the network away then), and a process started with the network and its logs, are `Provenance::Network`), and never lowers one the tool set itself. An unsandboxed command counts as using the network too, so in a tainted session it asks every time. A tool's own error (`ToolError`) gets its tool's declared source as well: from an outside source it's fenced (a redirect's `Location`, an echoed header, gh's stderr), and taints (a preview's error stays Marv's: a preview reaches nothing, so it's Marv's own refusal). The GitHub door's output is `Provenance::Github`. A saved output keeps its source, so reading it back fences and taints the same way. The session's own tools (the MCP adapter, `tool_search`, `mcp_call`, the mesh tools, `radio_tx`, the Herdr door) are pinned the same way. Guards: `untrusted_text.rs` (`every_tool_declares_a_source_class`, `the_session_tools_declare_their_sources_too`, `github_door_output_is_fenced_and_taints`, `network_command_output_taints_and_sandboxed_offline_output_doesnt`, `an_unsandboxed_commands_output_is_network_output`, `an_outside_tools_own_error_is_fenced_and_taints`).
- **Every tool result is tagged with its source.** Text that isn't from the user or Marv is fenced as data for the model; a closing tag inside it, in any case and however it's spelled (whitespace, invisible and default-ignorable characters and combining marks anywhere in it, lookalikes of `<` and `/`, and the letters' compatibility forms: fullwidth, mathematical, circled), is defused (`marv_core::defuse_closing_tag`), and the fence's attributes are escaped (`marv_core::escape_attribute`: `&`, quotes, angle brackets and their fullwidth forms; line breaks, line and paragraph separators and invisible characters as spaces), so neither the text nor a call's label (a URL the model wrote) can end the fence. An error result from an outside source is fenced too (an MCP server's JSON-RPC error message is its text, an error *result*, not Marv's error). Project checks and diagnostics are quoted, never spoken in Marv's voice. mesh_list fences each wired receptacle's description as its owner's data, and a failed mesh call or send, a failed wiring included, is quoted as mesh data and taints (the far end's error and the local switchboard's refusal arrive alike; guard `mesh.rs::a_failed_mesh_call_is_quoted_as_mesh_data_and_taints`). A subagent whose conversation was tainted has its report quoted as a subagent's data, Marv's own lines outside the fence, and the step the user declined (its model wrote the call) and its error text quoted too. Guards: `untrusted_text.rs` (`tainting_error_results_are_fenced`, `fence_attributes_are_escaped`, `closing_tags_hidden_by_invisible_characters_are_defused`, `mesh_list_descriptions_are_fenced`, `a_tainted_subagents_report_is_fenced`, `a_subagents_taint_reaches_its_parent_and_its_report_is_fenced`).
- **A project's instructions are the person's only once they trust them.** A project's `AGENTS.md`/`CLAUDE.md` (and its parent folders' up to the git root), its `.marv/skills`, its `.marv/agents`, its `.marv/roles` (chat roles) and its `.marv/team.md` (a team's shared brief, `marv_session::teams`) steer the model as the person's own words would, so a cloned repository's don't get that by being opened. Trust is per project and for exactly the files' contents (`marv_session::project_trust`, stored in `~/.marv/project-trust.json` beside MCP trust, hashed per file): a changed file asks again and names what changed. Each file is read once at startup and what's hashed is what's loaded (`load_project`); a trusted project skill's other files, read later, are checked against the hashes they were trusted with and quoted when they differ. Not trusted, the instruction files go to the model quoted as the project's data under Marv's fixed note, and the project's skills, agent types and roles aren't loaded or offered (in the TUI, the SDK and the desktop's `/` menu, role picker and New team dialog). The desktop's "Save as team file" (the person's click, after a confirm) trusts the files it wrote only when the project's files were the person's already, each written file loads exactly as the text Marv rendered, and nothing else changed meanwhile (`trust_after_write`). A role file is keyed by its file's name: one whose `name:` differs is a problem, not a role. A subfolder's instruction file, read when a tool first touches its folder, counts as the person's only when its own contents were trusted (`NestedTrust`), whatever the root holds (a project with no root files included): otherwise it's quoted, a notice names it, and `/trust` records it; nested files never speak in Marv's voice. File names in Marv's notes go through `printable()`. The TUI and the desktop say so at startup and `/trust` trusts what they showed, from the next start or chat (the system prompt and tool list stay byte-stable within a session). `marv -p` trusts only a stored, matching trust, or `--trust-project` for that run (nothing stored). Nothing is trusted by guessing (not the home folder, not a folder of the person's own commits). Guards: `untrusted_text.rs` (`an_untrusted_projects_instructions_load_fenced_and_offer_no_skills`, `a_changed_instruction_file_asks_for_trust_again`, `a_subfolder_instruction_file_counts_only_once_its_contents_are_trusted`, `a_trusted_skills_file_that_changed_since_is_quoted`, `an_untrusted_projects_roles_arent_loaded`, `an_untrusted_projects_team_isnt_loaded`, `saving_a_team_file_doesnt_trust_an_untrusted_project`, `saving_trusts_a_written_file_only_as_marv_rendered_it`, `a_role_file_named_otherwise_than_its_role_isnt_loaded`).
- **A session becomes tainted** once web, MCP, mesh or image content, a session-start hook's output (unless the user marked that hook `trusted`), what the Herdr door read from a pane (#74), the GitHub door's output, or a networked command's output enters its context. From then on, every `ToolKind::Egress` call asks, even in yolo:
  - network bash;
  - every MCP call, including tools marked `readOnlyHint`, except a read of your own remote app (below);
  - web requests to a new URL prefix (and a fetch's name reaches DNS only after its approval: the approval's preview refuses a private address literal or `localhost` without a lookup, and the lookup, with its check for a private answer, happens when the approved fetch runs, before it connects; a name can carry data, so a declined fetch must make no lookup at all. Guard: `web.rs::a_fetchs_name_is_looked_up_only_after_its_approved`);
  - mesh calls on unapproved wires;
  - writes to protected paths.
  - Not a read of your own remote app. A `readOnlyHint` tool of a remote (HTTP) server in your own `~/.marv/mcp.json` (Notion, Linear, Gmail: `McpTool::account_read`) only sends its arguments to that service, on your account, which shows nobody else what was searched, so it isn't a way out and runs unasked, like a GitHub read. Its output still taints. Never a project's server (`.mcp.json`) or a local one (a process on this machine can reach anything); the same server's other tools ask every time. The read-only claim is the server's own, and you chose to add it. Guard: `provenance.rs::your_own_remote_apps_reads_run_unasked_once_tainted_and_its_writes_ask_every_time`.
  - Not a GitHub door read. A read (`github::allow::classify`: gh's read commands and GET API paths; never a browser, git, a file, an upload, or a host other than the project's) only sends its arguments to GitHub's API, which shows nobody else who read what, so it isn't a way out and runs unasked as before. Its output still taints. GitHub writes and sensitive reads ask every time (`must_ask`). Guard: `github.rs::after_githubs_text_reads_still_run_unasked_and_a_write_asks_every_time`.
- **A mesh message that wakes an idle Marv (#78, `mesh.wake`; by default in the TUI only on a wire a rule the person made issued, runtime-kernel live UX, as the desktop) is read the same way:** only on a wire the user granted (by hand or by a rule), fenced as another agent's data, tainting the session before the woken turn's first request, never as a user message. So that turn's egress asks like any tainted turn's, in yolo too, and (#74) **it runs with automatic approval off**, like a radio turn (except that a sandboxed command without network still runs with the project read-only, `approveSandboxed`; a task turn's runs inside its role's write set instead): no yolo, no remembered or pre-approved "always", no approved URL prefix, every request `once` (`ToolContext::mode` without automatic approval; guard `mesh.rs::an_inbox_woken_turn_asks_for_what_yolo_would_allow`). Never while an approval waits, at most 3 wake-ups a minute per wire, and never in `marv -p`.
- **One check decides every wire, from the person's wires and the rules they made (runtime-kernel 2b).** `Switchboard::authorize` answers every "may this plug use that receptacle in this mode?": admitting a message, `tools/list` and `mesh_list`'s wired section, whether a message may wake its reader, and whether a `mesh_send`/`mesh_call` needs the wire prompt. The table's lookups are crate-only, and no other code decides from a snapshot. **Seeing is not permission:** `mesh_list` and `marv mesh ls` list the other Marvs, and that grants nothing (nor does `mesh_list` saying a rule covers one, runtime-kernel live UX: the send asks the rule again; guard `mesh_list_says_which_marvs_a_rule_covers_and_that_grants_nothing`); nor does being in the registry `mesh_list` reads (runtime-kernel 3: a desktop's chats and the scanned Marvs), which nothing that admits, wires or wakes reads. **A rule is the person's wire, and only that:** `~/.marv/mesh/policies.json` (the user's config folder only, absolute, 0600, never a project's, never a symlink; a file failing any check is no rules at all) holds rules the person made. Where the session honors them (desktop chats and the TUI, never `marv -p`), a rule covering both ends wires one Marv's main agent to another's main inbox without the wire prompt; it never covers a subagent, a shim plug, a Herdr pane or `watch`, and an end that doesn't honor rules asks its person. The wire's `policy` approver is made only by the switchboard's rule check, never deserialized (a peer's `marv/wire` can't claim it; a rule crosses as `peer_rule`), and the wire admits only while its rule is there and live: revoked or expired, the next message is refused. Rules are made only by the person's own tools: the desktop's Mesh panel and New team (`allow_folder`, `start_team`, on their click), `marv mesh allow` and `marv team start` (each written only after a y at a terminal). Guards: `tests/guards/tests/mesh_policy.rs` (`every_wire_check_goes_through_authorize`, `seeing_an_agent_in_mesh_list_grants_nothing`, `being_in_the_registry_grants_nothing`, `a_projects_policies_json_is_never_read`, `where_rules_arent_honored_a_matching_rule_changes_nothing`, `only_the_persons_own_tools_make_a_rule`, `rules_never_cover_a_pane_a_call_or_a_shim`, `a_rules_messages_are_fenced_tainting_bounded_and_end_with_it`).
- **A chat card carries the person's typed words to other Marvs' models only under a rule (runtime-kernel chat card, §5.6).** Each Marv's card is its conversation's first and latest person-typed lines (`Role::User`: never the model's replies, plan steps, tool output, mesh or radio messages, or a woken turn), each one printable line of at most 56 characters, plus when its last turn ended; no model call makes it. Its door's `marv/info` carries it to any Marv of the user's that lists the mesh folder, but `mesh_list` shows a card's words to a model **only for a Marv whose main inbox a rule the person made covers for the caller**; every other Marv is its name and a fixed state word, and subagents (never covered) see none. `"mesh": {"cards": false}` in the user's own config (default on; a project's config can't set `mesh`, and an unreadable config is off; not the radio's `titles`) stops the Marv publishing its card and showing others' words. A peer's card is never trusted: cut and cleaned again on receipt and where shown, unknown fields ignored, and shown as JSON strings fenced in `<untrusted-data source="mesh-card">`. **Taint (decided 2026-10-19, option B):** a list showing card words does **not** taint the reader: they are the person's own typed lines, at most 56 characters each, shown only under a rule the person made, and fenced (the radio's presence-title precedent); one constant (`marv_mesh::tools::CARD_WORDS_TAINT = false`) decides it. A list that reaches a Marv over a wire still taints as before. Known edge: text another agent typed into a TUI through an approved Herdr prompt, or a spawned worker's first task, is a user message there and can become its card. The event log never holds a card. Guards: `tests/guards/tests/chat_card.rs` (`model_tool_and_woken_text_never_become_the_card`, `a_cards_words_reach_only_covered_marvs_fenced_not_tainting`).
- **The team board is the rule's, its text is Outside, and it can't relay a read (runtime-kernel §19, T1–T7).** One small board per rule the person made (`~/.marv/mesh/boards/<rule>.json`: 0600, atomic, locked, unknown fields refused; deleted with its rule, and a post re-reads the rules under the board's lock, so it can't outlive a revoke). Every chat with mesh tools has `board_read`/`board_post`/`board_clear`; without a live rule covering the chat (or in `marv -p`) each says one fixed sentence and does nothing. The author is stamped by the chat's own Marv (its mesh name, never one of the reserved `you`, `user`, `the-user`, `person`), never taken from the model: a `by` in the call isn't the tool's (the schema repair drops it, or the input check refuses it), and whatever is posted is stamped anyway; a model clears only its own entries; the person posts and clears any from the desktop's Board tab. What `board_read` returns is other chats' words: fenced as `<untrusted-data source="board">`, one JSON line an entry, closing tags defused, and it **taints** the reader. A post needs no approval only where the chat could `mesh_send` under that rule (a `send` rule, on its sending side unless it's mutual: a message to the rule's own space, as a rule's send, D2), and only before the conversation read another chat (`chat_read`'s flag), or when everything it read was that same team's chats (see `chat_read` below). Under a read or call rule, on the receiving end of a one-way rule, or after a `chat_read`, each post asks the person, `once`, never yolo or a grant: a board can't widen a rule's direction or carry what a read rule allowed past it. A chat under two or more rules names the board it posts to (`rule`), or the post is refused. A clear takes only the chat's own entries and never asks. Limits: one line of at most 280 characters (no control, line or paragraph separator, bidi or other format characters), 5 live claims and 10 notes per author (a `done` closes a claim; an eleventh note drops the author's own oldest), 50 entries (a full board drops the poster's own oldest, and refuses a poster with none there: nobody pushes another's entry off), 24 h per entry. An expired rule's board goes at its next post and the desktop's rules look. A post wakes nobody and isn't mail. Logged as `board_post`/`board_cleared` events (who, kind, size, how many paths, how many cleared), never the text or a path. The board's file is outside every project (edit tools refuse it) and under `.marv/**` (protected) for a home project. Guards: `tests/guards/tests/board.rs`.
- **`chat_read` reads another of the person's chats only under a read rule they made, and never serves a tool's input or output (runtime-kernel §9.2, decisions R1–R5).** `read` is its own rule mode, off by default: a `send` rule never allows a read and a read rule never wires a message. Only the person makes one (the desktop's Mesh panel, "…and may read each other's chats", off by default; `marv mesh allow <folder> --read` behind the same y/N at a terminal). The reader's Marv checks the rule before it asks; the target's host checks it again over its door (`marv/read`), against the caller's pid-confirmed identity, before it reads anything, and nobody reads another process's session files by path (a terminal Marv answers only while it runs; a sleeping desktop chat from its saved session, without waking). Served: the chat's card, its stored compaction summary, and its last turns: what the person typed, what the assistant replied, and the names of the tools used, each turn one JSON object (so a quote can't fake a turn), best-effort redacted for secret shapes (`sk-`, GitHub tokens, JWTs, `NAME=secret`, credential URLs, PEM keys), at most 16 KB cut at a turn boundary. Never: a tool's input or output, Marv's notices, a woken turn's line, a mesh message, images or attachments, or anything from a chat the person marked **private** (desktop: the chat row's toggle; a chat without a record counts as private), nor the turn in progress of a chat mid-turn (it is served as of its last finished turn, its first line saying so; mk-60m.7, guard `tests/guards/tests/chat_read.rs::a_chat_mid_turn_is_read_as_of_its_last_finished_turn`). The reply reaches the reader fenced as `<untrusted-data source="chat-read">` and **taints** its session (`Provenance::Mesh`), so its egress outside the mesh asks from then on. The main agent alone has the tool, and only where the host honors the person's rules (the TUI, a desktop chat): never `marv -p`, an SDK session, a subagent or a pane. **No read-and-relay:** `chat_read` runs only in a turn the person started (a turn a mesh message or the radio woke is refused: "chat_read runs only in a turn you started"), and once a read is in a conversation (a flag that lasts as its taint does: compaction, resume) its mesh sends to the person's own Marvs lose a rule's no-ask (D2) and ask as tainted egress does, saying the conversation read another chat; so a send rule wider than a read rule can't carry what was read past it. **One exception, a team's own chats (desktop teams):** a read allowed by a team's read rule (labelled `Team <name>: read each other's chats`, made by the person when they start the team) is recorded by team (`TaintState::mark_read_team`, saved with the conversation as `read_teams`), not as the flag: sends over a wire that same team's rule issued, and posts to that team's board, still run as the rule lets them (`TaintState::read_confined_to`). Every other send and post asks as above: to a chat outside the team, over any other rule's wire, or once the conversation also read a chat outside the team or a second team's chat (no team carries another's words). The person put those chats in one folder and one team; a teammate's words going back to the team tell the team nothing a read wouldn't. A report still quotes no reply after any read. Guards: `chat_read.rs::a_teammates_read_still_sends_to_its_team_unasked`, `marv_sandbox::taint`'s `a_read_stays_inside_its_one_team`. 10 reads a minute per reader, burst 3, on both ends, refused reads counted too. Every read is a `read` event in the kernel's log (who read whom, what, the size, served or a fixed refusal reason), never the text; a served read is a quiet notice in the read chat, never the reader's words. Guards: `tests/guards/tests/chat_read.rs`.
- **Team mail carries its sender's taint (marv-rs, 2026-11-08).** A mesh message taints its reader (`Provenance::Mesh`) unless every message read came over a team rule's wire from a chat that had read nothing from outside when it sent: `Envelope::clean`, stamped by the switchboard from Marv's own main plug's turn (`TurnHop::watch_taint`/`clean`, never a subagent's plug, which shares the hop but not the taint) or a peer Marv's forwarded `marv/clean`, never from the model or the text (a shim's mail is never clean). - **Approvals show the full payload.** A network approval lists the scripts written this session that the command will run.
- **A network escalation is a network command, asked like one (#81).** A sandboxed command that failed like the missing network, retried without network (even with another tail), runs with `network: true` instead (`bash.rs`'s `repair`), so it goes through the approval for network commands and never runs on its own: in yolo too, since a network command is never `auto_safe`. A remembered or pre-approved "always" for that network scope answers it only where it answers any network command: not in a tainted session (`must_ask`), not in a turn without automatic approval (the radio's, a wake's: `once`), and a worktree subagent's automatic yes never covers it. With nobody to ask (`marv -p` without `--approve network`) it's refused before it runs. Guards: `approvals.rs::config_approve_never_covers_a_tainted_network_escalation`, `approvals.rs::an_escalated_retry_is_asked_in_a_turn_without_automatic_approval_and_in_a_subagent`, and `bash.rs`'s `with_no_one_to_approve_network_the_retry_is_refused_and_doesnt_run`.
- **Subagents don't inherit** network, web or mesh approvals — the config's pre-approved ones included (#98): `AlwaysScopes::for_subagent` strips the egress prefixes from the remembered scopes and the seeded ones alike.
- **`marv -p --dangerously-run-unsandboxed`, for a disposable container or CI machine only.** It turns the sandbox off for that run and approves every command (`bash:` scopes), so commands reach everything the user can. It exists for benchmarks such as Terminal-Bench, where each task runs in its own container and bubblewrap can't run inside it. It is a flag and nothing else: no `--approve` name, no config key (the config's `sandbox: false` plus every `approve` name still asks for each command, and `marv -p` refuses them), and the TUI refuses it (a person is there to answer). It prints a warning on stderr before anything runs. It answers nothing beyond commands: file changes, the web, MCP and the rest need their own `--approve` names, and the must-ask rules hold (egress after untrusted content needs `--approve-tainted`, a protected path `--approve-protected`). In practice a container run needs `--approve-tainted` too: an unsandboxed command had the network, so its output taints the session, and every later command is egress. Under the flag the file tools (`read_file`, `edit_file`, `write_file`, `apply_patch`) also reach outside the project, as its commands already do (`ToolContext::files_anywhere`): a path outside it is taken as given, with no project rule (the home folder's rule still applies); inside the project every rule holds as ever, protected paths included. Without the flag an outside path is refused as always (guard `only_the_flag_lets_the_file_tools_write_outside_the_project`). Guards: `tests/guards/tests/unsandboxed.rs`.
- **Pre-approved scopes (#98)** — the config's `"approve"` (and the TUI's `--approve`) seed "always, for this session" through the same path a person's answer takes, so they never cover what asks even in yolo: protected paths, `package.json` lifecycle scripts, mesh wires (`once` + `must_ask`), tainted egress, and any file change when the project is the home folder (`once`, or a home folder's `files:home:` scope, which only a person's "always" answers). `marv -p` keeps its own `--approve` list out of the seeds, so a subagent's `for_subagent` is what bounds them; the flag list itself behaves as before.
- **A command that changes the repository without asking keeps git's program parts read-only (Linux).** With yolo or `approveSandboxed`, a sandboxed `git_write` command without network runs unasked when the project's `.git` is a plain folder with a plain `config` (`git_guard::git_write_supported`: not a worktree's `.git` file, no symlinks among the parts below) and the project isn't the home folder; otherwise it asks, as before. It runs with `.git` writable and mounted on itself (so it can't be renamed away and replaced by one with a planted config), and read-only on top of that (`Plan::read_only_on_top`, after the writable mounts): `config` (hooksPath, fsmonitor, aliases, drivers, sshCommand), `hooks/`, `info/`, `modules/` and `worktrees/` (other repositories' config and hooks), `config.worktree` and `commondir` (where git looks for all of those). A missing folder gets an empty read-only placeholder; a missing `config.worktree` or `commondir` is created first with content that changes nothing (empty; `.`), mounted read-only, and removed afterwards, so git outside the sandbox (an editor's `git status`) never follows a planted one while the command runs, as it would if it were only removed afterwards. An exclusive lock on `.git` (`git_write_guard`) keeps two such commands (subagents, another Marv) from sharing those stand-ins. Objects, refs, the index, HEAD, logs and a merge's or rebase's state stay writable: commits, branches, merges, rebases, stash and tags work. A command that looks like it changes the repository's setup (`git config`, `remote`, `submodule`, `worktree`, `init`, upstream tracking, hook installers; bash's `GIT_SETUP`) is asked as before so it works; that list is a convenience, never the rule: the mounts are. Seatbelt (macOS) keeps asking. Known limit: like any project file a command may change, a rebase left in progress can hold `exec` lines that `git rebase --continue` runs on the machine. Guards: `sandbox.rs::an_unasked_git_write_commits_but_cant_reach_what_git_runs`, `approvals.rs::approve_sandboxed_still_asks_for_network_git_write_the_host_and_without_a_sandbox`.
- **Extra writable sandbox folders (#98)** — the config's `"writable"` is the one way a sandboxed command writes outside the project. Entries are canonicalised (symlinks followed) and refused at startup, not mounted: `/`, the home folder and its parents, the project's parents (other projects' `.git`), **any hidden top-level entry of the home** (`~/.<anything>`: the entry, anything inside it, or a parent of it — `.local/bin`'s planted binary runs on the host, `.config/autostart` and `.config/systemd/user` run at the next login, `.claude`'s hooks run on the host; only a *visible* top-level tree like `~/Projects/…` is allowed), **a git repository** (the entry is one, sits under a `.git` path component, or directly holds a `.git` entry — a worktree's `.git` file included; a planted `.git/hooks` script runs on the host's next git command there; a repository planted *deeper inside* an accepted folder later is not scanned — the refusal happens once, at startup), the mesh's runtime sockets (`$XDG_RUNTIME_DIR/marv`, anything in it or holding it), **Marv's own config folder** wherever `MARV_CONFIG_DIR` puts it (anything in it or holding it: its `config.json` holds the API key and the session-start hooks, and it holds the tool-output files), and anything missing or not a folder. Refused entries become startup problems, never mounts. An entry in the project (writable already) or inside another entry is left out quietly: a sandboxed command could swap its parent for a symlink, and the next command's bwrap would bind wherever that leads read-write.
- **`marv -p --approve` never answers a call that asks every time.** Tainted egress needs `--approve-tainted` as well as the call's `--approve` scope, and a protected-path write needs `--approve-protected` as well as `--approve files`; otherwise the call is refused (in `refused`, exit 3, a stderr line naming the flag). Subagents reach the same approver. The SDK hands the request to the client's approver with `must_ask` set, and an approver that answers from a policy should refuse it the same way. Guards: `tests/guards/tests/headless_taint.rs`.

## Chat roles (runtime-kernel coordination)
- **A chat's role bounds its tools for its whole life.** A role (`.marv/roles/<name>.md`, the project's only once trusted; `~/.marv/roles`; the built-in `coordinator` and `worker`; `marv_session::roles`) is picked when the chat starts (`marv --role`, the desktop's new-chat picker), saved with the session, and a resume into a session saved with another role is refused. A tool its `tools:` doesn't list (the coordinator: no `edit_file`, `write_file`, `apply_patch`) isn't offered (the main agent's list and a subagent's), and `run_tool` refuses a call to it anyway, before anyone is asked (`ToolContext::tool_allow`). Guard: `tests/guards/tests/roles.rs` (`run_tool_refuses_a_tool_the_role_doesnt_allow`).
- **A role's write set is enforced on the edit tools, and in the sandbox for bash and background processes.** With `writes:` (project-relative folders or files, never globs, never `..`, never `.git` or another protected path such as `.marv`, `.env*`, `AGENTS.md`; `[]`: no file changes), `edit_file` and `write_file` refuse a path outside the prefixes in their plan, so before any approval and again at apply time under the file lock, with a message naming the allowed prefixes. The check is on both the path as written (after `..` is resolved) and where it really leads, so a symlink inside a writable folder pointing elsewhere is outside (`marv_tools::write_set`). A sandboxed bash command, and every background process the chat starts (`ProcessManager::bound_writes`), sees the project read-only with each prefix that exists bound read-write on top, a prefix that is a symlink only when where it leads is itself in the set; read-only folders and protected paths inside a prefix stay read-only (bwrap's later read-only binds; Seatbelt's protected denies, which now apply whenever a writable folder sits inside the read-only project). **Tool caches:** a role may also list `tool_cache` paths (the built-in devserver and reviewer: `node_modules/.vite`, `node_modules/.cache`; `tool_cache:` accepts only cache-like paths, a role-load error otherwise: under `node_modules/`, or ending `.cache*`, `.vite`, `.turbo`, `.parcel-cache` or `.next/cache`; `dist` is not one) that only its commands (bash, `process`) may write: bound read-write like a prefix, the edit tools still refuse them, ignored for a role without `writes`; Marv creates a missing one only when its parent already exists as a folder inside the project (canonicalized, the folder made as that real parent plus the single name and checked again with `symlink_metadata`; never in a home-folder project; `write_set::existing`). Guards: `marv_tools::bash::tests::a_read_only_roles_tool_caches_are_writable_for_its_commands`, `roles::tests::run_and_verify_roles_may_write_only_the_listed_tool_caches_and_say_so`. **Gaps:** a prefix that doesn't exist yet can't be created from bash (write_file can); an approved `git_write` can't write `.git` under a write set; bash outside the sandbox (`sandbox: false`, the host door, or the sandbox off or missing) isn't bounded by the write set (those commands are asked every time); and between the edit tools' last check and their write, a symlink another process swaps in could redirect the write (the check runs again under the file lock just before writing; an `O_NOFOLLOW` write isn't done). Guards: `tests/guards/tests/roles.rs` (`the_edit_tools_refuse_paths_outside_the_roles_write_set`), `tests/guards/tests/process.rs` (`a_process_is_bounded_by_the_roles_write_set`), and `crates/marv-session/tests/process_tool.rs::a_role_chats_processes_are_bounded_by_its_write_set` for the session's wiring), `marv_tools::bash::tests::a_role_write_set_leaves_only_its_prefixes_writable`, `marv_sandbox::seatbelt::tests::a_writable_folder_in_a_read_only_project_keeps_the_protected_denies`.
- **A task turn runs only what stays inside the role, only for the senders the role names, and only for a message a person's turn sent over a rule's wire.** A mesh wake is a task turn (`CallMode::Task`, `marv_session::task_report`) only when all hold: the waking message was sent at hop 0 (from a turn the sender's person started); it came over a wire a rule the person made issued; and the role's `takes_tasks_from` names the sender, by the role it publishes on its door (`PeerInfo::role`: the peer's own claim, so it can only widen what runs unasked inside this chat's own bounds) or, for a desktop chat only (a stable mesh name from its chat id, as its door confirmed it when the wire was made), by that name. A report never starts one. **The hop rule, exactly:** a turn a mesh message woke runs at hop 1 or more whatever the message carried (a shim's or a Herdr pane agent's carry no hop), so a coordinator another agent woke can't make a task turn elsewhere; a timer the person scheduled starts at hop 0 like their own turn (accepted: it's their act), but any woken turn (a timer's too) that reads a message that isn't a stamped report rises to one past the deepest hop read, or to 1 when none carried a hop. A person's own turn stays at hop 0 through the replies it waits for (stamped reports, and mail sent at hop 0 from a turn its person started: the lead pattern), but reading any other outside message (a higher hop, or none) raises it to at least 1 for the rest of the turn, so its later sends can't start a task; the person's next message starts at 0 again. A task turn reads only that sender's hop-0 messages that aren't reports, at its start and between steps, and its `mesh_wait` waits only for those; anyone else's, that sender's from deeper in a chain, and its reports wait unread for a later ordinary turn. An edit inside the role's write set runs without asking (a role without `writes` that has an edit tool, like the built-in frontend, backend and worker, is bounded by the project folder as a person's yolo turn is: the Demo2 test showed requiring a set made every Start-team task ask; a role with no edit tool and no `writes`, a custom `tools: [read_file, bash]` role, is treated as `writes: []` in a task turn, `ToolContext::task_read_only`, so its commands see the project read-only and a `process` start asks; guards `a_bash_only_role_without_writes_cannot_write_the_project_in_a_task_turn`, `in_team_never_gives_the_coordinator_or_a_writes_nothing_member_writable_bash`, `a_task_turn_without_a_write_set_still_asks_for_protected_paths_and_home_folder_edits`), as does a bash command yolo would run (sandboxed, no network, no git_write) and, only for a role whose own `tools:` lists `process`, a `process` start without network (`marv_tools::floor::task_auto_runs`; `apply_patch` isn't included until it's built). Everything else asks, once, as in any woken turn: egress (tainted), `sandbox: false`, git_write, a networked process, paths outside the set (refused), protected paths, Herdr, MCP. Every woken inbox turn reports back to its sender's inbox when it ends (and once when it starts waiting for its person), built without a model call, over an existing wire or one a rule issues (never one a person must approve), sent in the background. A report is Marv's fixed words (the kind, the files changed, a declined tool); it quotes the model's reply (its first paragraph) only for a task turn whose wire back a rule issued, in a conversation that read no other chat. **Team rework (Demo2): a coordinator turn rooted only in a team task's stamped report sends tasks.** Without this a team's rework stalled: the coordinator's turn woken by a worker's report runs at hop 1, so its `mesh_send` reached the worker as an ordinary woken turn that asks for every edit. A stamped report also says whether it answers a task (`Envelope::task`: the reporting turn was itself a task turn, taken from `InboxTurn::task` by Marv's own report code, stamped like `report`, forwarded by a pid-confirmed peer's plug as `marv/task`, never from text and never without `report`). A turn woken by a stamped report that answers a task, over a wire a rule labelled `Team <name>` issued, is *team-rooted* in that rule (`TurnHop::root_in_team(rule)`, set by the session at the turn's start); its sends over a wire that same rule issued are then stamped hop 0 by the switchboard (`admit_claiming`, only for Marv's own plugs and only for the rooted rule's wires, so rework never crosses to another team the coordinator is under), and the receiver applies its unchanged task rules (hop 0, a rule's wire, `takes_tasks_from`). So every hop-0 link in the chain traces back to a turn the person started: the first task is hop 0 from the person's turn, a worker's task-turn report answers it, and only that report roots the rework. A report from an ordinary woken turn (every woken inbox turn sends reports, a waiting one too) answers no task and roots nothing, so team mail the person never started, or one that overrode a decline they gave, can't become a task. The root ends at the turn's end and the moment the turn reads anything but team task reports (any other mail, a report that answers no task, a message at any other hop, a radio message, a report over a non-team wire: `inbox_read`; a `chat_read`, `board_read`, `mesh_call` or `herdr` call: `SessionToolRunner::run`), and every new turn starts unrooted (a person's turn still rises to 1 on outside mail; a timer turn is never rooted and still rises on hop-less mail); forged report text is ordinary mail that wakes, raises the hop and roots nothing. Still bounded by the 30/h team budget and the 60 wakes until the person types, by the role's write set and the task floor (egress, git_write, protected paths still ask). Accepted: a worker's report text can steer the coordinator's rework, which now starts an unasked-within-the-write-set task; the same bounds apply. Guards: `roles.rs::a_teams_follow_up_rooted_only_in_task_reports_is_a_task`, `a_declined_edit_stays_declined_through_a_teams_ordinary_mail`, `a_teams_task_report_roots_the_rework_and_the_chain_continues`, `a_rooted_coordinator_sends_tasks_only_over_the_rooting_rules_wire`, `a_rooted_coordinator_that_reads_other_mail_mid_turn_sends_no_task`, `a_rooted_coordinator_that_reads_a_chat_or_the_board_sends_no_task`. **A report is stamped, not read from text:** `Envelope::report` is set by the switchboard only for text the sending session armed in its own turn state (`TurnHop::arm_report`, from `task_report::send_report`: the end report and the waiting report; a model's `mesh_send` and a sandboxed command on the plug's socket can't) or forwarded by a pid-confirmed peer Marv's plug (`_meta` `marv/report`, believed like the hop); a peer without the flag sent no report. The text starts with `Marv report from ` for people only: a message that merely starts so is ordinary mail (it wakes and counts like any). A report never wakes its reader, so two chats can't keep each other going (`WakeSkip::Report`). **Accepted risk:** a stamped task report from a team worker may quote that worker's reply (its first paragraph), so the worker, or text it read, can steer what the coordinator's next task says; it is bounded by the rule the person made (only a rule's wire, only listed senders) and by the receiving role's write set, and a report never starts a task itself. Guards: `tests/guards/tests/roles.rs` (`a_task_wake_needs_a_listed_sender_and_task_mode_still_asks_outside_the_role`, `a_task_needs_hop_0_and_a_rules_wire`, `a_task_turn_reads_only_its_senders_messages`, `a_task_turn_reads_only_its_senders_hop_0_messages`, `a_turn_a_shim_woke_never_sends_a_task`, `a_person_turn_that_read_outside_mail_sends_no_task`, `a_timer_turn_that_read_hopless_mail_sends_no_task`, `a_message_that_only_starts_like_a_report_is_not_one`, `a_teams_follow_up_rooted_only_in_task_reports_is_a_task`, `a_report_quotes_the_reply_only_for_a_task_over_a_rules_wire`, `a_report_never_wakes_or_starts_a_task_turn`, `task_mode_runs_process_unasked_only_for_a_role_that_lists_it`, `task_mode_without_a_write_set_is_bounded_by_the_project`, `a_start_team_workers_task_turn_runs_its_edits_and_sandboxed_bash_unasked`).

## Compaction and saved pages (#63)
- **Taint survives compaction.** A summary can paraphrase untrusted text and the v2 tail carries it verbatim, so no compaction path touches the session's taint: the v1 and v2 summaries, overflow recovery's summaries and its level-3 drop of the oldest messages. A session tainted before is tainted after, in memory and in the saved session (dropping the turns that held outside text doesn't take back what the model may have acted on). Fences in kept turns keep their bytes. Guard: `tests/guards/tests/compaction.rs::taint_survives_compaction`.
- **What a compaction replaces is saved before it's replaced.** The paged-out turns go to the conversation's own swap folder next to its saved file (`<id>.swap/<n>.jsonl`, 0600 in 0700 folders, like sessions; it holds untrusted text, as the session file does), each with its source; the folder may not be a symlink, pages are numbered under a lock and never overwritten. The page is written before the summary is asked for. A write that fails fails the compaction and the history is kept, except in overflow recovery, where the turn goes on without the page and a notice says so. A live session holds its swap folder; one whose session file is gone, or that is older than the saved tool outputs' 7 days, is removed at a later session's start (`SessionStore::remove` deletes a session with its pages, for when sessions can be deleted). Guards: `compaction.rs::a_page_out_writes_swap_before_replacing_the_history`, `a_symlinked_swap_folder_is_refused`, `pages_are_never_overwritten`, `saved_pages_age_out_but_never_a_live_sessions`.
- **The page table is Marv's.** The list of saved pages at the end of a summary is built from the calls' runs, never from the model's summary: only calls that worked, paths resolved inside the project, control characters dropped, at most 200 characters, each shown as a JSON string (a path can't add a line to the list); saved outputs from the saved-outputs folder by call id. A list of saved pages in the model's own summary is removed before it's installed. Guards: `compaction.rs::the_page_table_is_written_by_marv`, `a_page_table_path_is_capped_at_200_characters`.
- **A recalled page keeps its source.** `recall` gives back each web, MCP or other outside result in a fence of its own source (a closing tag inside is defused) and marks the session tainted by each again: reading a page back can't turn outside text into trusted text. Guard: `compaction.rs::a_recalled_page_keeps_its_provenance`.
- **`recall` reads only its own conversation's pages.** It takes no session id or path; the main agent's context names the current conversation's swap folder, a subagent's names none (and its tools don't include `recall`), so another chat's or the parent's history isn't reachable through it. Guard: `compaction.rs::recall_reads_only_its_own_conversation`.
- **Nothing is retrieved on the model's behalf.** Saved pages come back only as the result of a `recall` call; the history is rewritten only at a compaction, and the tool list never changes at one (`recall` is offered from the start). Guard: `compaction.rs::the_tool_list_is_byte_stable_across_a_page_out`.

## The context budget and page-out events (runtime-kernel §11, private)
- **A chat's context budget is set only by its person.** The size at which the kernel pages a chat out is `min(85% of the window, the person's budget for the chat or compactTokens)`. The per-chat budget comes only from the person: Marv desktop's chat settings or `/compact budget` (a `Configure`), 40k to 10M tokens, saved with the session; never from a tool, the model's text, a project's files (`.marv/config.json` is never read for it) or a mesh message. A saved value outside that range (a hand-edited or planted session file: too small compacts every step, too large never compacts a model whose window isn't known) is dropped on resume. A desktop skill named like a built-in command isn't offered, so a project can't take over `/compact`. It never goes past 85% of the window. Guard: `tests/guards/tests/memory_manager.rs::the_context_budget_is_set_only_by_the_person`.
- **A page-out's kernel event is sizes, never text.** `compacted` lines in the event log carry the chat, a fixed word for what started it (`budget`, `overflow`, `person`), the overflow level, the context before and after, the summary's cost, the page's number and its turn count: never the summary, a turn or the person's `/compact` focus, and the format has no field one could go into. Guard: `memory_manager.rs::compacted_events_carry_sizes_never_text`.
- **A chat card's context numbers are numbers within limits.** The card's `context_used` and `context_budget` are the chat's own numbers; a peer's are cut to 10M tokens where they're read, a used count without a budget isn't shown, and they're shown as Marv's words, outside the card's fenced words, under the same rule as the words. Guard: `memory_manager.rs::a_cards_context_numbers_are_numbers_within_limits`.

## The doors out of the sandbox (Marv Sprint 4)
Narrow, named ways out, each with what it can never do. A door's own program (`gh`, `herdr`) is taken only from an absolute PATH entry, by its real path, and never from inside the project or a sandbox-writable folder, where a sandboxed command could have put one (`marv_sandbox::host_env::host_program`). The mesh's Herdr panes (`mesh_cmd::start`, `marv mesh ls`) take `herdr` the same way, and offer no panes when none is found. In a home-folder project the home is the project, so a `gh` or `herdr` under `~` (`~/.local/bin`) is skipped and that door isn't offered there: it fails closed. A call through one carries its door on the approval (the prompt shows the door's warning line), on its result and in the trajectory. The doors are the main agent's: a subagent's context has none.
- **github** (Marv #47) runs gh with the user's login, outside the sandbox:
  - never: `auth`, `config`, `extension`, `alias`, an unknown first word (an alias or extension), `secret`/`variable`/`ssh-key`/`gpg-key`, `--web`, `gh api --input`/`--verbose`, downloads, `repo clone`, `pr checkout`, another GitHub host than the project's. Refused before anyone is asked, whatever the approver says;
  - writes, other API methods, fields, graphql and sensitive API reads (secrets, keys, hooks, emails…) ask, in yolo too; a sensitive read is asked every time (`once`);
  - gh is spawned without a shell, without Marv's keys or debug switches, with `GH_HOST` pinned to the project's host (github.com where origin names none), and its git never runs the repository's programs;
  - GitHub token shapes are redacted from what gh prints before the model, the events, the saved session or the trajectory see it;
  - a subagent only reads; offered only where gh is there and logged in; `marv -p` needs `--approve github` for a write.
- **host** (Marv #52) is bash with `sandbox: false`, one command on the user's machine:
  - asked every time (`once`: "always" never covers another), in yolo too;
  - only where someone approves each command at a terminal (the TUI; the SDK's `host_commands`): refused before any ask in `marv -p`, in an SDK session without `host_commands`, and for a subagent;
  - its environment is the user's minus Marv's keys and anything secret-looking (`marv_sandbox::host_env`); token shapes are redacted from its output.
- **herdr** (#74) drives Herdr, the terminal multiplexer Marv runs in, from Marv's own process (the `herdr` CLI, through mesh v2's adapter). Offered only when Marv starts in a Herdr pane (`HERDR_ENV`), fixed for the session; the sandbox still can't reach Herdr (its variables cleared, its socket hidden: #130), only the door can:
  - **reads run without asking** (list workspaces, tabs, panes, agents; a pane's status; a pane's last lines). What comes back is other programs' text (screens, names and titles anyone can set): it's `Provenance::Herdr`, fenced as data (`<untrusted-data source="herdr">`) and it **taints** the session, like a mesh message;
  - **light actions ask** (focus, rename, a prompt typed into an idle agent's pane), "always" allowed (`herdr:focus`, `herdr:rename`, `herdr:prompt:<pane>`). A prompt is never a command (the pane send's rule, #128: text starting with `/`, `!` or `#` is refused before anyone is asked). In a turn the person didn't start (a mesh wake or the radio: `ToolContext::mode` without automatic approval), they're asked `once`, like every request there: no remembered "always" answers them;
  - **running anything is asked every time** (`once`: never remembered, not by "always", the config's pre-approved scopes or yolo): `run` (a command in a new pane) and `spawn` (a Marv or another Herdr agent kind, optionally in a new git worktree). The approval shows the exact command, the folder or branch, the worker's kind and its task. Only where someone approves each one at a terminal (`Doors::herdr`, the TUI's main agent, as `host`): refused before any ask in `marv -p` (with every `--approve` name: none covers `herdr:`), in an SDK session without `host_commands`, and for a subagent (which isn't offered the tool at all);
  - **a spawned worker gets no more than its parent:** a Marv starts with the user's config only (never the session's `--approve` scopes or remembered answers), and with `MARV_YOLO=off` (which can only turn yolo off; `/yolo on` is refused there) unless the spawning turn is in yolo; another agent kind starts with no arguments a model chose (the tool has no field for them). At most `herdr.peers` panes per session (the user's own config; default 4, 0 to 16), checked before anyone is asked; a pane Herdr no longer has doesn't count;
  - **taint isn't laundered through another agent:** a worker spawned from a tainted conversation starts tainted (`MARV_TAINTED=1` on a Marv's command, which can only add taint; it shows a startup note and marks `Provenance::Herdr` at its first turn, so its egress asks). A prompt or spawn in a tainted conversation is egress (`must_ask`) and its approval says "The receiving agent will treat this text as your own words, with its own approvals.";
  - **nothing a model passes reaches the `herdr` CLI as an option:** ids start with a letter or digit, and a rename's name, a run's command and a prompt or task (`pane_prompt`, the mesh's pane sends too) can't start with `-`. A run command can't start with `^` (quick substitution) or hold `!` (history expansion), invisible format characters, line or paragraph separators or the Hangul fillers; one that starts an agent gets a warning pointing to spawn;
  - the panes it opened outlive the turn and are the user's: `/peers` lists them, `/peers read <name>` shows one's last lines, `/peers stop <name>` closes one (never the model's to do). `/exit` and Enter (or ctrl+c) are typed only into an agent that's idle or done: one that's working or at an approval gets nothing typed (Enter would answer its question) and its pane is just closed; a pane that's already gone is forgotten. A worktree stays until the user removes it. Pane names, titles and output reach the terminal only through `printable()`.

## Provider keys and subscription sign-ins (#159)
- **Each provider gets only its own credential.** OpenRouter's key (`apiKey`, `OPENROUTER_API_KEY`) and the Z.ai Coding Plan's (`zaiApiKey`, `ZAI_API_KEY`) are separate fields and variables, and the ChatGPT sign-in is its own file: a provider without its credential asks for it (setup opens), it never borrows another vendor's. Guard: `tests/guards/tests/subscriptions.rs` (`a_providers_key_never_goes_to_another_provider`).
- **A custom provider gets only the key in its own entry, and only from the user's own config (#275).** `"providers"` is read from `~/.marv/config.json` alone (there is no project layer), so a repository can't add an endpoint or redirect one. An entry's `key` (`env:NAME`, `command:...` or the key itself) is sent only to that entry's `baseUrl`; a built-in provider's key (saved or in the environment) is never sent to it, and its key is never sent to a built-in provider. A key that can't be read (an unset variable, a failing `command:`) fails every request with the reason instead of sending one without it. A `command:` helper runs once per process on the host, as the user wrote it (like a session-start hook): `sh -c`, the host door's environment (Marv's keys and secret-looking variables left out), stdin closed, 30 s at most; only its first output line is used, and it's never shown. Guard: `subscriptions.rs` (`a_custom_providers_key_is_its_own`).
- **A local llama-server is Marv's alone (#278).** The `llama-server` Marv starts for a GGUF model listens on 127.0.0.1 only, on a free port, with a random `--api-key` (32 random bytes) that only Marv's requests carry: a sandboxed command with the network shares the loopback, and must not use the server or make it load other models. The server is the user's own program (from their `PATH` or their config's `llamaCpp.server`, never a project's), started outside the sandbox like Ollama's daemon, with the host door's environment (Marv's keys and secret-looking variables left out), in its own process group, stdin closed, its output in a private (0600) log under `~/.cache/marv`; Marv stops every server it started when it exits. Known limit: a Marv killed with SIGKILL leaves its server running. Guard: `crates/marv-session/tests/local_model.rs` (`a_local_model_runs_through_the_llama_server_marv_starts_and_stops`: the host, the key on every request, stopped with Marv).
- **Marv's own secrets never come back in a tool result (marv-rs, 2026-11-06).** Every result and label leaves `run_tool` (the one place a tool runs) with the secrets Marv was configured with replaced by `[redacted: a secret from Marv's configuration]`, before it reaches the model, the stream, the transcript, the saved session or the trajectory: each built-in provider's saved key and its environment variable, a custom provider's key (and headers), the key the session was given, and the MCP servers' tokens (secret-looking stdio environment values, auth headers; read again each turn). Values under 8 characters aren't treated as keys. Unsandboxed, a model `cat`ed Marv's config.json and the OpenRouter key went to the model and into the run's logs (Terminal-Bench). `Secrets`' `Debug` shows only a count. Known limits: a cut result's full copy in the session's own tool-output folder (inside Marv's config folder) is saved before the redaction (reading it back through a tool is redacted); ChatGPT and MCP OAuth tokens live in their files and aren't in the list; a key added mid-session with /setup may not count until Marv restarts. Guards: `tests/guards/tests/secrets.rs` (`run_tool_redacts_configured_secrets_from_every_result`, `an_unsandboxed_run_that_cats_marvs_config_never_sends_its_keys`).
- **A plan's limit is a hard stop.** A usage-limit error from a plan ends the turn with Marv's message; it's never retried like a passing rate limit and never answered by switching keys or providers (`errors::plan_limit`). Guard: `plan_limit::a_plans_limit_is_a_hard_stop`.
- **Sign in with ChatGPT's loopback listener** (`marv_provider::chatgpt`) binds 127.0.0.1 only (never `0.0.0.0`, never `localhost`), answers only `/auth/callback`, takes exactly one callback (the first carrying the sign-in's `state`, compared in constant time; others get a page and are ignored), stops listening after it, and gives up after 5 minutes or when setup closes. Connections are answered side by side, each given 2 s for its request line, so an idle local connection can't hold the callback up (guard `sign_in_listener::an_idle_connection_doesnt_stall_the_sign_in`). A sandboxed command shares the loopback network: without the state it can't feed Marv a code. The browser page echoes nothing from the request; a refusal is shown only as a short code. PKCE (S256) and the ID token's checks (RS256 against OpenAI's JWKS, issuer, audience = the issued client id, expiry, nonce) mean a code alone is worth nothing. Guards: `sign_in_listener::the_sign_in_listener_is_loopback_only_needs_the_state_and_takes_one_callback`, `sign_in_listener::the_sign_in_listener_times_out`.
- **Its token goes only to OpenAI's public API** (`https://api.openai.com/v1`): a config's `baseUrl` is ignored for ChatGPT, and the token file must be an absolute path (no fallback to a file in the working folder). Guard: `the_chatgpt_token_is_never_sent_to_another_host`.
- **Its tokens stay in Marv's config folder.** `~/.marv/chatgpt.json` (or `MARV_CONFIG_DIR`'s), 0600 in a 0700 folder, written atomically and refreshed under a lock across Marv processes. The config folder is hidden from every sandboxed command; the tokens are never put in an environment, a log, the transcript, an event or a trajectory, and the stored record's `Debug` leaves them out. Guard: `sign_in_listener::the_sign_in_tokens_never_show_in_debug_output`.
- **Marv never sends another app's OAuth client id.** The sign-in registers dynamically (`dynamic_agent_client` under Marv's name) and then uses the client id OpenAI issued in the callback; the Codex CLI's is never used. Each registration (an issued client id and the account it was issued for) keeps its own tokens: one registration's client id is never paired with another's tokens. The authorize address shown on screen leaves out the `id_token_hint` (a token); only the browser gets it.

## MCP
- Project servers need trust. The hash covers the entry and the files its command runs.
- `npx`/`uvx` run outside the project folder.
- Server `instructions` are ignored.
- Tool descriptions in Marv's deferred-tools note and in `tool_search`'s answer are fenced as MCP data (`tool_search` caps each at 1,000 characters); they don't taint, since the person installed the server. The specs sent as tools can't be fenced and stay as the server wrote them (capped at 2,000 characters). Guard: `untrusted_text.rs::mcp_descriptions_in_announce_and_tool_search_are_fenced`.
- **A server may ask nothing of Marv.** The client advertises no capabilities (`"capabilities": {}` in `initialize`): no `sampling` (a server may not spend the person's model or money), no `roots` beyond the project path Marv passes, no `elicitation`. A request from a server other than `ping` is answered "method not found". Guard: `tests/guards/tests/devices.rs::the_mcp_client_advertises_no_capabilities`.
- **A conversation's MCP tools are fixed at its first turn.** A server added (`/mcp add`, the desktop's gallery), logged in or changed later is offered from the next conversation (a new one, `/clear`, a resume), never mid-conversation: its tool specs are part of the cached prefix, so the tool list is fixed for a conversation. A server's annotations (`readOnlyHint`) are refreshed only for the next conversation; mid-conversation, a reconnected server that drops its read-only claim is taken at its word (the stricter of the two), one that adds it isn't. Deferred, `tool_search` and `mcp_call` reach only the conversation's own tools too. Guard: `devices.rs::mcp_add_never_changes_a_running_conversations_tool_list`.
- **A server's tool list is read once, at start.** `notifications/tools/list_changed` is ignored: the tool specs are part of the cached prefix, and a server adding a tool mid-conversation would be adding words to it. A change takes effect when Marv next starts. Guard: `devices.rs::list_changed_never_changes_a_running_tool_list`.
- **An add approval says what a yes can't pin, in fixed words.** `/mcp add` (and the desktop's gallery) shows the exact entry it writes. For a package runner (`npx`, `uvx`, `bunx`, `pnpx`, `uv`) it adds that the package is pinned but its own dependencies follow their version ranges, so a later start can run newer code; for a remote server, that it is whatever its owner deploys and the yes approves the address, not what runs there later (`install::proposal::{RUNNER_CHANGES, REMOTE_CHANGES}`). Likewise a project server's trust hash covers its entry and the files its command runs, not what a remote server or a package's dependencies become. Known and unchanged.
- **Installing a server is the person's act, never a tool's.** Writing `~/.marv/mcp.json` (`/mcp add`, `/mcp remove`, the desktop's gallery) and trusting a project's servers (`/mcp trust`, the startup question) happen only in the shells' code. Guard: `devices.rs::no_tool_installs_a_driver` (a source check).

## File changes
- **No write over a change the session hasn't seen.** Two Marv sessions in one folder, a subagent, a command or the person in their editor can change a file after the model read it; an edit built on the old text would silently drop that change. Each session keeps a content hash (SHA-256) of every file it read (`read_file`, any page; a `grep` hit doesn't count) or wrote (`marv_tools::file_versions`). `edit_file` and `write_file` (appends included) on an **existing** file refuse when the file's hash now differs from the session's, or when the session never read it; nothing is written and no one is asked (the check runs in the preview, and again at apply time). A file that changed since the session saw it is refused with an error telling the model to read it again. A file the session never read at all is refused with its current text in the refusal (the whole file up to 400 lines, else 400 around `old_string`, numbered like `read_file`), and that shown version is recorded as seen, exactly as a `read_file` of it would be, so the model's next call can succeed; a change after that is refused like any other. A secret's name (`.env*`, `*.pem`, `id_*`) and a binary file are never shown: the plain refusal stands. A new file needs no read, and is created only if it still doesn't exist (a file someone made meanwhile is refused as never read). The session's own write is its new version: the formatted file when the formatter ran on exactly that write, else what it wrote, and if the file no longer matches (the write failed, or the file changed right after it) the next write is refused with a message that says so rather than blaming another session. A partial read counts as seen (the hash is the whole file's). At most 10,000 files are remembered per session, least recently used out first; a forgotten one must be read again. A subagent has its own hashes; /clear and a resume start empty. `bash` writes aren't tracked, so a file a command changed must be read again before an edit. A command's output counts as reading a file only when what the model was shown (after the cut) holds the file's whole current content verbatim (`marv_tools::shown`: `cat src/a.js`, a `for … cat` loop): that version is recorded as seen, as `read_file` would; a partial view (`head`, `grep`) doesn't count, a secret's name never does, and a change after it is refused as before. Guards: `tests/guards/tests/stale_writes.rs` (`an_edit_after_another_sessions_write_is_refused_until_reread`, `an_existing_file_never_read_cant_be_overwritten`, `a_file_a_command_showed_whole_counts_as_read_and_only_then`).
- **The check and the write are one step, across processes, and no lock outlives a call.** Inside the in-process per-file queue, the edit tools hold an advisory `flock` on a per-file lock file in the runtime folder's `file-locks/`, or `~/.marv/file-locks/` where there's no runtime folder (both hidden in every sandbox, so a command can't hold one), for the check, write and format of that one call, never across a model step or a turn; the OS drops it if Marv dies. Both locks are keyed on the file's resolved real path (`~/`, `..` and symlinks resolved; the name case-folded on macOS and Windows), so every spelling of a file is one lock. A call that can't get it within 20 s, or whose wait is ended by Esc, fails and writes nothing. Known limits: hard links to one file are separate locks, and Marv processes using different lock folders (a different `MARV_RUNTIME_DIR`) don't see each other's; the content check still applies to both. Guards: `stale_writes.rs` (`the_check_and_write_are_atomic_across_processes`, `no_lock_outlives_one_call`, `a_home_spelling_of_a_file_waits_for_the_same_lock`).

## Subagents and children
- **No tool writes Marv's config.** Onboarding, `/setup` and the TUI's settings commands, and the desktop's settings are the only writers of `~/.marv/config.json`, all person-driven; Marv's config folder is outside every project, so the edit tools refuse it. Guard: `tests/guards/tests/boot.rs::no_tool_writes_marvs_config` (a source check, and the edit tools refused in yolo).
- **A child gets narrower, never wider.** A subagent's context is built from scratch: no memory, no agent host (no subagents of its own), its type's tools within the parent's (never `agent` or `memory`), no network, web, MCP or mesh "always" answers, its parent's taint (which flows back), its parent's yolo and "no automatic approval", and its tokens count in the parent session's totals. A worktree subagent is the same, in its worktree. A Marv the Herdr door spawns is a new process with the person's own config only, yolo held off (`MARV_YOLO=off`) where its parent was out of yolo and tainted (`MARV_TAINTED=1`) where its parent was. A resumed conversation keeps its own taint. Guards: `boot.rs` (`a_subagents_context_is_narrower_never_wider`, `a_subagent_is_offered_tools_within_its_parents_and_spends_its_parents_budget`), with `provenance.rs::subagents_inherit_taint_but_no_egress_approvals`, and `herdr.rs` (`a_spawned_worker_never_gets_more_than_its_parent`, `a_worker_spawned_from_a_tainted_conversation_starts_tainted`).

## Images (marv-rs)
- **Sources:** the person (a paste, which Marv saves under `pasted/`, or a file their own message names: typed, dragged, `~/…`) and `read_file` on an image inside the project (a screenshot of what an agent built). Never a woken turn: a teammate's, a timer's or the radio's message naming `~/.ssh/id.png` attaches nothing (`only_the_persons_own_message_attaches_images`). Never web, MCP or mesh content: their tools return text.
- **Trust follows the source,** as for text: a person's image is theirs (Authority); a project file's is Workspace, like the project's other files, so it doesn't taint. A page fetched into the project and screenshotted is no different from one curled into a file and read. This replaces the earlier plan of a quarantined reader for every image and a taint on any image: an agent checking its own screenshot would then have needed a yes for every report to its lead (the same stickiness that made `chat_read` ask for every team message).
- **The quarantined reader** is still used for a chat model that can't read images: a tools-less request to `visionModel` (default `anthropic/claude-haiku-5.5`, OpenRouter only) writes the description, labelled with the model's name, in the image's place.
- **No decoding:** Marv reads only the header (type by magic bytes, width and height) in safe Rust, refuses anything but PNG, JPEG, GIF and WebP, and caps an image at 5 MB. The bytes go to the provider as they are. Saved copies (pasted images, the trace's `<session>.images/`) are 0600.
- **Cost:** a request carries only the newest 4 images; older ones are named in a line of text.

## Claude Code chats (the harness plan, phase 1)
A Marv desktop chat can be run by the person's own Claude Code (`marv_web::claude_code`) instead of Marv. Marv drives `claude -p` over its stream-json mode, as the Claude Agent SDK does. Marv doesn't run Claude Code's tools, so most of this document doesn't apply to them, and the page says so: the new chat's note, every card ("Claude Code's own tool: Marv's sandbox doesn't apply") and the header's title.
- **Not Marv's guarantees.** Claude Code's commands and edits run as Claude Code runs them: its own sandbox setting, permission mode and allow lists, as the person. Marv's sandbox, protected paths and taint tracking don't cover them. Nothing Claude Code reads taints anything in Marv directly. Since phase 3 it reaches other chats only through the mesh, and its mail counts as tainted (below).
- **Every permission prompt comes to the person.** It starts with `--permission-prompts host --permission-prompt-tool stdio`, so each prompt Claude Code would show reaches Marv as a `can_use_tool` request and becomes an approval card ("Claude Code asks"). A decline, an interrupt, or a page that's gone denies it. What Claude Code doesn't ask about (its own allow lists, or a mode the person set in Claude Code) runs without a card, as in a terminal.
- **The chat's yolo is Marv's yolo (consistency finding H4).** A Claude Code chat set to yolo starts with `--permission-mode acceptEdits` and `Bash` allowed: edits and commands run unasked and a web fetch still asks, as Marv's yolo does. Only inside the outer sandbox (phase 4), which confines them as Marv's sandbox confines Marv's; outside it the chat asks and says why. Never where Marv holds yolo off (a folder whose config turns it off, the home folder). A change mid-chat starts its process again with the new setting (it resumes the conversation). Guard: `a_harness_chats_yolo_is_marvs_yolo` (`marv_web::claude_code`).
- **A terminal chat's permission mode: Full access only inside the outer sandbox, never above Supervised in the home folder.** Each agent chat has one of the same modes for every agent (`marv_web::terminal_agents::Permissions`: its own settings, Supervised, Auto-accept edits, Auto, Full access), set on its agent its own way when its terminal starts (`permission_settings`: Claude Code's `--permission-mode`, Codex's `--sandbox`/`--ask-for-approval`, Gemini's `--approval-mode`, OpenCode's `permission` config, Marv's `--approve`). Full access asks for nothing, so the desktop turns the outer sandbox on for it, refuses to start the chat where bubblewrap can't run, and `terminal_agents::command` refuses it for any agent but Marv (which sandboxes its own commands) when the sandbox isn't on. Wherever Marv holds yolo off (the home folder or above it, a project's `"yolo": false`), every mode above Supervised runs as Supervised (`Permissions::held`). Only the person picks a mode (the chat's header, Settings' default for new chats). Guard: `marv-web` `terminal_agents::tests::full_access_runs_only_inside_the_sandbox_and_never_in_the_home_folder`.
- **An agent chat's `delegate`: the person approves each one, the delegate works sandboxed, one level deep, and its reply is another agent's words.** An agent chat's mesh server offers `delegate`, `delegate_wait` and `delegate_cancel` (`marv_session::delegate`) when the desktop gives it a host (`ChatSpec::delegates`, `crate::delegates` in the desktop). `delegate` starts another installed agent in a new chat in the same folder (and worktree), with the asking chat's permission mode; it's asked of a person every time (`needs_approval` and `once`: never yolo, a grant or a remembered "always"), showing the agent and the whole task. The delegate gets only the task, never the conversation, and starts unattended, so inside the outer sandbox (`start_chat_terminal`'s `unattended`; its permission mode's own rules on top). A delegate's chat gets no `delegate` tools and `start_delegate` refuses a delegate's call: no chain of agents starting agents. `delegate_wait` returns the delegate's reply fenced as `<untrusted-data source="delegate">` (closing tags defused) and taints the asking session, as mail does. A chat sees and stops only its own delegates (`Delegations::status`/`owns`). Guards: `marv-session` `delegate::tests` (`a_delegation_asks_the_person_each_time_and_says_what_it_starts`, `waiting_gets_the_reply_fenced_and_tainting`) and the desktop's `delegates::tests::a_delegates_turn_is_the_one_after_its_task`.
- **Its turns meet the person's budgets (H2).** Before each turn its meter starts and every budget over the chat is checked (`marv_web::harness_budget`, the same rules as a Marv turn's): a person's turn at a limit asks (a card no "always" answers), an unattended one pauses. Each turn's reported cost goes to the meters (Settings → Spending, the event log), and an unattended turn carrying the chat's grant charges the grant, so its daily cap holds. Claude Code reports cost once per turn, so a turn already running isn't cut off mid-way: the next one meets the limit. Guards: `a_claude_code_chats_turn_asks_at_its_budget` (`app/src-tauri/src/chats.rs`), `a_harness_chats_turns_meet_the_budgets_and_charge_the_grant` (`marv_web::harness_budget`).

Pause can't wait for the end of a step, so it stops the turn and says so. Guard: `stop_and_pause_stop_a_claude_code_chats_turn` (`app/src-tauri/src/chats.rs`).
- **"Always" is for this chat only.** Claude Code suggests rules it would save in its settings files (the project's, the person's), which would outlive the chat and apply to every `claude` in the folder. Marv sends every rule back with `session` as its destination, so the card's "for this chat" is true (`in_this_chat`).
- **Marv's keys stay with Marv.** Claude Code uses the person's own Claude login. The chat's OpenRouter key is never passed, and Marv's own variables (`MARV_*`, `OPENROUTER_API_KEY`) are removed from its environment. The person's other variables (an `ANTHROPIC_API_KEY`) are left for Claude Code.
- **Only `claude-code`, only if installed.** `create_chat` refuses any other harness name, and refuses Claude Code when no `claude` is found. A Claude Code chat takes no role.
- Guards: `tests/guards/tests/claude_code.rs` (`always_on_a_claude_code_card_stays_in_this_chat`, `a_decline_denies_and_marvs_key_never_reaches_claude_code`, run against a stand-in `claude`).

Opening it, a message or a timer loads it again with `--resume`. A timer runs only under the chat's live grant (the person's "keep working while you're away"), within the same daily timer limit, and under the same 30-minute deadline as a Marv chat's unattended turn: past it, or when the grant ends, the turn is stopped and the chat paused. - **A worktree of its own, if asked.** Marv's write sets and roles don't bound Claude Code's edits, so a new Claude Code chat in a git folder can start in its own worktree (a new branch from the last commit, under `~/.marv/worktrees`). Settings → Harnesses tells whether a Claude login was found from the `ANTHROPIC_API_KEY` variable or the presence of `.credentials.json`. Marv never opens that file.

- **Phase 3: on the mesh with Marv's own mesh tools, and its mail is never clean.** A Claude Code chat has a door like a Marv chat. Claude Code reaches the mesh only through an MCP server Marv OS runs for that chat (`marv_web::harness_mesh`, a 0600 socket in the chat's mesh folder, joined to Claude Code's stdio by `marv __mesh-mcp`). It offers `mesh_list`, `mesh_call`, `mesh_send` and `mesh_wait` on the chat's main plug, and they run in Marv through `run_tool`. So a send with no wire asks the person (a card in the chat; the other Marv's person too), a rule the person made answers first, and the switchboard checks, limits and logs every message. These tools are pre-allowed in Claude Code (`--allowedTools`) only because Marv does the asking. Guard: `a_harness_chat_has_the_board_and_chat_read_under_the_same_rules` (`tests/guards/tests/board.rs`). Nobody registers a turn for the harness's plug, so its mail is never clean: a Marv chat that reads it is tainted. Mail for it is fenced as another agent's words, with Marv's note that it isn't the person's. It arrives as a woken turn's message (within the same wake rules as a Marv chat), at the end of a mesh tool's result, or under the person's next message.
- Guards: `a_claude_code_chats_mesh_send_asks_for_its_wire_and_its_mail_is_never_clean` (`tests/guards/tests/claude_code.rs`), `mail_on_the_mesh_wakes_a_claude_code_chat_fenced_loaded_or_asleep` (`app/src-tauri/src/chats.rs`).
- **Phase 3, part 2: a team member, bounded as far as Marv can bound it.** A Claude Code chat can start as a team member with a role. At start it's told its role's prompt and the team's brief (`marv_session::teams::harness_brief`, the same sections and bounds as a Marv member's). Marv doesn't run its tools, so the role's tool list binds it only by its own word, and the brief says so. **Its write set is enforced (H6)** inside the outer sandbox: the project is read-only and only the set's prefixes are writable on top (`harness_sandbox::bound_to_role`, as Marv's own sandboxed commands see a bounded role). A missing prefix is made as a folder first, only where what exists of it is inside the project. Outside the sandbox nothing enforces it, and the chat says so once. The chat's plug has a turn hop with no taint on it. Its sends then carry a hop: its inbox reads raise the hop past the deepest message read, so chains still stop. The mail stays unclean. A woken turn is a task turn by the same decision as a Marv member's (`task_report::inbox_turn_for`, now shared). When it ends, Marv sends the sender a stamped report (`task_report::harness_report`): only over a wire that exists or a rule issues, never one a person would have to approve. It quotes the reply only for a task turn back over a rule's wire, and otherwise uses Marv's fixed words.
- Guard: `a_claude_code_members_task_turn_reports_back_like_a_marv_members` (`tests/guards/tests/roles.rs`); the turn hop in `mail_on_the_mesh_wakes_a_claude_code_chat…`; the write set: `a_harness_members_write_set_is_all_its_agent_can_write` (`tests/guards/tests/claude_code.rs`, real bubblewrap).
- **Phase 4: the outer sandbox.** Where bubblewrap works, each `claude` process runs inside Marv's own sandbox (`marv_web::harness_sandbox`, built by `marv_sandbox::bwrap::sandbox_args`), unless the person turned it off in Settings → Harnesses (`harness_sandbox`, on by default).
  - **What it can reach:** the chat's folder is writable (and, for a worktree, the repository's shared `.git`), and network is on.
  - **Claude Code's config:** its own config is bound back in writable: `$CLAUDE_CONFIG_DIR`, or `~/.claude` and `~/.claude.json`.
  - **What's hidden:** the rest of the home is the stand-in home. Toolchains are read-only, and SSH, GPG, cloud logins, browsers, keyrings and other projects are hidden. Marv's config and runtime folders are hidden too, so no other chat's mesh plug is reachable, and `/run` is empty.
  - **Protected paths:** unlike a Marv command, it may change `.git`, `CLAUDE.md`, `.env` and the other protected paths, because a coding agent commits and edits its own instructions. Only `.marv/` stays read-only.
  - **Environment:** cleared, but for Claude Code's own variables (`ANTHROPIC_*`, `CLAUDE_*`, proxies, CA files, `USER`), never `MARV_*` or the OpenRouter key.
  - **Mesh helper:** a chat on the mesh gets only its own MCP socket and the plain `marv` helper, at `/run/marv-harness/`.
  - **The `claude` program:** a mise shim or wrapper is resolved to the real binary first, since mise writes in the hidden home.
  - **Without bubblewrap:** it runs as in a terminal, and the chat says so once. The cards' note says which way it runs.
  - **The PATH inside:** mise's tool folders (`mise bin-paths`, found outside) come first and its shims are dropped: a shim runs `mise`, which would try to repair its symlinks in the read-only installs folder and fail.
- **An agent's Home chat asks before each change.** An agent chat can be started on Home (the home folder as its project). There the outer sandbox is always on, whatever Settings → Harnesses says, and without bubblewrap the chat doesn't start (`create_chat` and `claude_code::home_unsandboxed` refuse it).
  - **What it can reach:** the home is writable (`Plan::home_writable`, bubblewrap only; Seatbelt refuses such a plan), with the home-folder masks still on top: every hidden top-level entry, SSH, GPG, cloud and agent logins, keyrings, browsers, sockets. Marv's config and runtime folders stay hidden. Only the agent's own config is shown again, over its mask (`Plan::over_masks`), so it's signed in.
  - **Every card is asked:** its cards are yes-or-no and must be answered by the person (`claude_code::home_card`: `once`, `must_ask`), so no earlier "always" answers one. Yolo is refused in the home folder, as for Marv.
  - **Not covered:** commands the person pre-allowed in the agent's own user settings (Claude Code's `~/.claude/settings.json` allow rules) run without a card, as they would in a terminal.
- Guard: `an_agents_home_chat_writes_the_home_but_not_its_secrets_and_asks_every_time` (`tests/guards/tests/claude_code.rs`, real bubblewrap, a fake home). Proven: the agent's config bound before the masks, the masks skipped for a writable home, and `home_card` leaving the card as it came each failed it.
- Guard: `claude_code_in_the_outer_sandbox_sees_its_project_and_config_and_nothing_else` (`tests/guards/tests/claude_code.rs`, real bubblewrap, a fake home). The real `claude` was checked once by hand (`harness_sandbox::live`, ignored): it answered, and `~/.claude.json` stayed writable.
- **Phase 4: agents over ACP (OpenCode, Gemini CLI, Antigravity).** `marv_web::acp` drives `opencode acp`, `gemini --acp` or `agy acp`, each the person's own install and login, over the Agent Client Protocol. The guarantees are Claude Code's:
  - **Permission prompts:** every `session/request_permission` is an approval card that says who asks, answered with the agent's own option (allow once, its "always" for that session, reject). A stop is `session/cancel`, and a pending card is answered cancelled.
  - **OpenCode's defaults:** OpenCode would run its edits, commands and fetches unasked by default, so Marv starts it with them set to ask (`OPENCODE_CONFIG_CONTENT`). A chat set to yolo, inside the outer sandbox, starts it with edits and commands allowed and fetches still asking: Marv's yolo (H4). Gemini CLI's and Antigravity's yolo isn't set by Marv yet: they ask by their own settings, and a yolo chat says so. A yolo change applies at the agent's next start.
  - **Budgets, Stop, roles:** as Claude Code's (H1, H2, H6 above): the same runner seams (`harness_budget`, the interrupt as `session/cancel`, `bound_to_role`).
  - **What Marv offers:** the client offers no `fs/*` or `terminal/*`.
  - **Mesh:** the agent reaches it only through the same MCP server (`session/new`'s `mcpServers`), and its mail is never clean.
  - **Environment:** Marv's keys and variables are removed.
  - **Outer sandbox:** it runs inside, with its own folders bound back in writable (OpenCode's `~/.config/opencode` and `~/.local/share/opencode`, Gemini's and Antigravity's `~/.gemini`), created first so a first run's login and sessions survive. Its own variables (`OPENCODE_*`, `GEMINI_*`, `GOOGLE_*`) are the only ones passed.
  - **Start lines:** ACP has no system prompt, so a chat's start lines (the mesh line, a team member's role and brief) go before its first message, once per session.
