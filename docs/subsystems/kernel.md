# marv-kernel

The runtime kernel planned in `docs/architecture/runtime-kernel.md`: who the agents are and, phase by phase, the
policies that let them talk, the scheduler, the registry and the event log. New in marv-rs: Marv (TypeScript) has no
original, so there's nothing to port. Depends on `serde`, `serde_json`, `thiserror` and `marv-fs`; pure data and
decisions (no sockets, no Tokio, time passed in), below `marv-mesh`, except `store.rs`, which reads and writes the rules
file through `marv-fs`.

**§20: the visible OS (M12).** Every Marv on the machine in one table (the desktop's Activity tab and
`marv kernel ps`), each from its own door's `marv/info` (`live`: core, context, the last minute's model / tools /
waiting-for-you split, tokens/s, cache hit %, $/h, throttles, subagents, real processes), the log as fixed sentences
(`marv kernel log`, the timeline, "while you were away"), notification history in memory, Permissions (show and
revoke) and About. For the person only: nothing here reaches a model (`docs/SECURITY.md`, guards
`tests/guards/tests/visible_os.rs`).

**Phase 3: the registry and the event log.** `mesh_list` reads a registry (the same answer as a door scan, byte for byte), and the person's own Marvs log the kernel's events to `~/.marv/events/` (never a message's words), which `marv kernel replay` rebuilds.

**Phase 2b: live comms under the person's rules.** A rule the person made wires two Marvs' main agents with no wire
prompt on either end (desktop chats and the TUI; never `marv -p`), sends on that wire ask nothing per message (D2,
`docs/SECURITY.md`), and what it wired ends at the next message once it's revoked or expired.
